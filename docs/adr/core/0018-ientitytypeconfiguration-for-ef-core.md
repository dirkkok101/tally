# ADR-CORE-0018: IEntityTypeConfiguration for EF Core

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** Accepted
**Origin:** Standard EF Core practice, adopted by Identity (ADR-0018), adopted by Actions on independent merit.

## Context

EF Core entity configuration can be done via `OnModelCreating` overrides, static `ModelBuilder` extension methods, or `IEntityTypeConfiguration<T>` classes. As the entity count grows (Actions has 22 entities), a single `OnModelCreating` method becomes unmanageable.

## Decision

Use **`IEntityTypeConfiguration<T>` classes** — one per entity — auto-discovered via `ApplyConfigurationsFromAssembly()`.

**Standardised configuration order:**
1. `ToTable()` — schema and table name
2. `HasKey()` — primary key
3. `ConfigureTrackedEntity()` / `ConfigureTenantEntity()` — shared base configuration
4. Properties — column types, conversions, constraints
5. Soft delete — `HasDefaultValue(false)` + `HasQueryFilter(e => !e.IsDeleted)` for `ISoftDeletable` entities
6. Relationships — navigation properties with explicit `OnDelete` behaviour
7. Indexes — performance and uniqueness constraints

**Rules:**
- Every FK must have explicit `OnDelete` (CASCADE, Restrict, or SetNull) — see ADR-0020
- Enum properties use `HasConversion<string>()` with `HasMaxLength()` — see ADR-0004
- `JsonDocument` columns use `HasColumnType("jsonb")` with custom value comparers
- Translation tables use composite unique: `(EntityId, LanguageId, TenantId)`

## Consequences

**Positive:**
- One file per entity — easy to find, review, and maintain
- Assembly scanning is framework-supported (`ApplyConfigurationsFromAssembly`)
- Configuration order is standardised across the team
- Each config class is independently reviewable and diffable

**Negative:**
- Assembly scanning for EF configs while banning it for DI (ADR-0021) is a minor inconsistency — justified because EF configs implement a known interface with clear semantics
