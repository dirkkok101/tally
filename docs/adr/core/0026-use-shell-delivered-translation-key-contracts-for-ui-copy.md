# ADR-CORE-0026: Use shell-delivered translation key contracts for UI copy

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** Accepted
**Origin:** translation closeout review

## Context

ADR-CORE-0013 covers translated entity values such as names and descriptions, but it does not govern static Angular UI copy such as page titles, column headers, form labels, validation messages, empty states, confirmation dialogs, and action buttons. Actions owns application translation keys and default values for the Actions product surface. Identity owns languages, translation storage, and language selection. Without a dedicated rule, new modules can satisfy entity i18n while still shipping hardcoded English in the UI.

## Decision

All user-facing static UI copy in NxGN Actions must use shell-delivered translation key contracts. The backend ActionsTranslationKeys contract, ApplicationTranslationKeyRegistry, and ApplicationTranslationCatalogue define the canonical keys and default English values. The Angular shell receives the key contract, stores it through TranslationKeyContractService, and components use ngx-translate through TranslatePipe or TranslateService. Grid column definitions, enum labels, confirmation text, validation messages, toast text, and computed option labels must be built from translation keys and must refresh when the active language changes. API-provided translated entity values remain data and should not be retranslated in the client. Raw English is allowed only in tests, seed/default catalogue values, technical identifiers, and data returned by APIs.

## Consequences

Every new UI module must include translation contract, registry, catalogue, TypeScript model, test fixture, and component usage work before it is considered complete. Module designs and implementation plans must call out translation-key coverage explicitly. Reviewers can treat hardcoded visible English in Angular templates or component code as a defect. This adds a small amount of ceremony, but it keeps Actions aligned with Identity-owned language support and prevents late-stage localization refactors.

## Alternatives

Relying only on entity i18n was rejected because it misses static UI copy. Embedding local translation key strings directly in Angular components was rejected because it bypasses the shell contract and can drift from backend registration. Letting Identity define Actions UI keys was rejected because Actions owns its product vocabulary while Identity owns language capabilities and translation persistence.
