# ADR-CORE-0027: Use DbContext Factory and Optional Shared Context for Queries and Commands

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** Accepted
**Date:** 2026-05-02
**Deciders:** Actions engineering
**Origin:** Review follow-up 2026-05-02

## Context

Actions queries and commands need predictable DbContext lifetime, retry-safe transactions, tenant-context propagation, and composition across aggregate operations. The intended standard is that any DbContext-backed query or command can run independently, or can participate in a caller-owned context and transaction when composed with other operations. Earlier documentation over-emphasized write commands: several query examples still injected scoped ActionsDbContext directly or created a factory-owned context without an optional shared context parameter. That let implementation drift by feature and made transaction-spanning behavior depend on each author instead of the platform contract.

## Decision

All production queries and commands that touch ActionsDbContext use IDbContextFactory<ActionsDbContext> in public constructors and expose an optional ActionsDbContext? dbContext parameter after CancellationToken on their execution method. For commands this is ExecuteAsync(..., CancellationToken ct = default, ActionsDbContext? dbContext = null). For query-like services the same rule applies to ExecuteAsync, WriteAsync, EvaluateAsync, or the method that performs the database operation. When dbContext is null, the operation owns a short-lived factory-created context; owned commands that open explicit transactions run through EF Core execution strategies. When dbContext is supplied, the operation participates in the caller-owned context and current transaction and never disposes it. Internal test constructors may accept ActionsDbContext directly, but production DI must not.

## Consequences

Queries and commands can be composed inside one caller-owned transaction without changing their normal standalone behavior. Retry-enabled providers can safely replay owned command transactions without reusing a failed DbContext. Read queries can share the same tenant-scoped context as surrounding write logic when consistency matters. Transactional audit rows can commit or roll back with the aggregate mutation by passing the shared context to IAuditService.LogAsync(..., dbContext). The cost is a small amount of owned/shared context boilerplate; the platform keeps this contained through DbContextFactoryExtensions and architecture guard tests.

## Alternatives

Scoped ActionsDbContext injection was simpler but made transaction composition, context lifetime, and retry behavior inconsistent. Factory-only operations without an optional shared context were rejected because they cannot participate in caller-owned transactions. Ambient transactions were rejected because they hide ownership and interact poorly with EF execution strategies. Separate audit contexts were rejected for business audit entries that must be atomic with the state change. A full unit-of-work wrapper remains deferred because the immediate need is a clear query/command contract backed by PAT-CORE-API-COMMANDS, PAT-CORE-API-QUERIES, and architecture guards.
