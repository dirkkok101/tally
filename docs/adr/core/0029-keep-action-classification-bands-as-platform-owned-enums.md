# ADR-CORE-0029: Keep action classification bands as platform-owned enums

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** Accepted
**Date:** 2026-05-04
**Deciders:** AMPS architecture
**Origin:** Research requested 2026-05-04 after clean-system E2E lookup review.

## Context

ADR-CORE-0004 permits C# enums for system-owned finite states, while ADR-CORE-0028 requires owning admin modules for tenant-configurable lookup data. Browser E2E and clean-client commissioning raised whether Priority, RiskLevel, SourceSystem, EvidenceType, and HierarchyOfControls are tenant-configurable. These fields drive escalation matrices, compliance guard logic, M2M application isolation, evidence upload semantics, and safety-control ordering across multiple modules. Treating them as tenant rows would make guards, reports, integrations, and cross-tenant behavior depend on mutable configuration rather than a stable platform contract.

## Decision

Priority, RiskLevel, SourceSystem, EvidenceType, and HierarchyOfControls are platform-owned finite classifications and must remain C# enums stored with EF HasConversion<string>() unless a future accepted ADR supersedes this decision. Tenants configure behavior around these classifications through owner modules such as Escalation Rules and Compliance Profiles, but they do not create, rename, delete, or reorder the classifications themselves. RiskLevel remains the canonical platform band set Low, Moderate, High, Extreme for guard and reporting semantics. If clients need custom risk scoring, labels, or likelihood x consequence matrices, introduce a dedicated tenant Risk Matrix admin module that maps tenant-specific rows to these canonical bands rather than replacing the canonical enum. SourceSystem is an integration identity/app-isolation concept, not a tenant lookup; adding a new source system requires a platform integration decision and Identity/application registration alignment. EvidenceType is an evidence media/category contract for upload semantics, not a tenant document-type catalogue. HierarchyOfControls follows the fixed safety-control hierarchy used by ISO 45001/NIOSH/OSHA guidance; tenants configure whether and when HoC enforcement applies, not the hierarchy values.

## Consequences

No admin modules are required for these five classifications. Existing enum lookup endpoints and translation keys remain valid for display, while mutable tenant setup remains focused on true owner modules. Guard evaluation, escalation rules, app isolation, reporting, and browser E2E stay deterministic across tenants. The trade-off is that tenant-specific risk or evidence terminology cannot be represented by editing these enum values; that requirement must be modeled as a separate owner module with explicit canonical mapping if it becomes product scope.

## Alternatives

Make every dropdown tenant-configurable: rejected because it would add admin surfaces for platform semantics and break deterministic cross-module behavior. Add mutable seed rows only for tests: rejected by ADR-CORE-0028 because it hides missing product surfaces. Replace RiskLevel with tenant risk matrices immediately: rejected because current PRDs only require canonical high/extreme guard behavior and do not define a risk-matrix module. Treat SourceSystem as tenant data: rejected because M2M app isolation and Identity client registration are platform integration contracts. Treat HierarchyOfControls as tenant data: rejected because the ordered hierarchy is a regulatory/safety framework, while enforcement configuration already belongs to Compliance Profiles.
