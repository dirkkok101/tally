# ADR-CORE-0030: Keep Tally provider-neutral and delegate transport orchestration to Hermes

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** Accepted
**Date:** 2026-07-20
**Deciders:** Dirk
**Origin:** Cross-module Tally documentation review and corrected system-boundary decision

## Context

Tally is a local financial domain system consumed by an external agent ecosystem. Hermes orchestrates AgentMail, WhatsApp, and other local services. If Tally owns mailbox polling, MIME parsing, provider cursors, sender or recipient policy, message acknowledgement, schedules, delivery, or retries, provider details become finance-domain semantics and duplicate Hermes responsibilities. Tally still needs durable and auditable finance operations, privacy-conscious evidence references, structured clarification and reconciliation results, and stable automation contracts without depending on any provider.

## Decision

Keep Tally provider-neutral and expose its capabilities through typed, versioned commands and structured results. Tally owns canonical financial facts, evidence metadata and opaque external references, reconciliation, classification, budgets, insights, idempotency, and audit history. Hermes is an external orchestrator that owns AgentMail and WhatsApp integration, mailbox and MIME handling, provider cursors, sender and recipient controls, acknowledgement, clarification conversations, schedules, rendering, disclosure policy, throttling, delivery, and retries. Tally does not poll providers, interpret provider identifiers, send notifications, or know delivery channels or recipients. The CHANNELS graph area is not a Tally implementation module; it may remain temporarily as an external-consumer boundary while references are migrated, then may be removed.

## Consequences

Benefits: finance behavior remains deterministic, testable, reusable across providers, and isolated from transport credentials and payloads; Hermes can change providers without changing Tally semantics; all callers receive the same exact command and result contracts. Costs: Hermes is required for conversational and scheduled experiences; contract compatibility and end-to-end observability span two systems; provider failures and delivery state cannot be diagnosed from Tally alone. Existing documentation that assigns screens, conversation, scheduling, notification, or delivery to CHANNELS must be revised to name an external orchestrator boundary. Tally modules must return enough structured state, exceptions, and opaque evidence references for Hermes to orchestrate safely without private-store access.

## Alternatives

Integrate AgentMail and WhatsApp directly into Tally: rejected because it couples finance semantics and privacy boundaries to current providers and duplicates Hermes. Keep CHANNELS as an internal Tally delivery module: rejected because orchestration and recipient policy already belong to Hermes and would create two owners. Add a generic transport abstraction inside Tally: rejected because provider-neutral interfaces would still place delivery lifecycle inside the wrong system. Move finance workflow and reconciliation decisions into Hermes: rejected because canonical invariants, idempotency, audit history, and deterministic financial results must remain inside Tally.
