# Nearest-ancestor Category Budget Entry resolution over frozen Spend Category ancestry

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** accepted
**Ref Code:** DD-BUDGET-CATEGORY-ENVELOPE-RESOLUTION

## Description

Resolve which Category Budget Entry governs a Budget Actual whose Spend Category is a descendant of the planned category, without double counting any Budget Actual. The flat exact-identity rule reported a Budget Actual on a nested Spend Category as Unbudgeted Spend even when an ancestor carried the intended shared Planned Spend, which prevented detailed classifications from consuming one shared parent envelope.

## Decision

Each Budget Actual resolves exactly one governing Category Budget Entry by scanning its frozen Spend Category ancestry from self toward root and selecting the first ancestry element that carries an explicit entry in the bound Budget Plan Revision. LEDGER supplies that ancestry as ActualsPageItem.FrozenAncestryIds, ordered root-first with the assigned Spend Category as the final element, so the scan runs from the last index to index zero and the nearest explicit entry wins.

Resolution outcomes are exhaustive and mutually exclusive. A resolved entry with Planned Spend greater than zero places the Budget Actual in the Budgeted position of the resolved Spend Category. A resolved entry with Planned Spend equal to zero places it in the Zero Budget Position of the resolved Spend Category, so an explicit zero-amount descendant entry is an allocation that terminates the scan and blocks fallback to a funded ancestor. When no ancestry element carries an entry, the Budget Actual is Unbudgeted Spend keyed by its exact assigned Spend Category identifier, not by any ancestor. A Budget Actual with no assigned Spend Category remains Uncategorized Spend.

Every Budget Actual is assigned to exactly one position. A position row reports the partition of its own total: DirectActualMinorUnits covers Budget Actuals whose exact assigned Spend Category equals the row category, DescendantActualMinorUnits covers Budget Actuals absorbed from descendant Spend Categories that carry no nearer entry, and AbsorbedCategoryIds lists those descendant identifiers in ascending ordinal order. ActualMinorUnits equals DirectActualMinorUnits plus DescendantActualMinorUnits exactly; the partition never adds to the row total and never republishes a descendant Budget Actual in both a descendant row and an ancestor row. Absorption applies only to rows produced by a Category Budget Entry. An Unbudgeted Spend row therefore never absorbs anything: it is keyed by one exact assigned Spend Category, its direct actual equals its row actual, its descendant actual is exactly zero, and its absorbed identifier list is empty. Two unfunded Spend Categories in the same unfunded ancestry produce two separate Unbudgeted Spend rows rather than one aggregated ancestor row.

The public BudgetActualMember contract gains AncestryIds, carrying the same root-first self-last frozen ancestry, and EffectiveCategoryId, carrying the resolved Spend Category identifier or null when the outcome is Unbudgeted Spend or Uncategorized Spend. Because BudgetActualMember is the budget.insights.evidence.get surface, one public read reports the effective envelope for each individual Budget Actual.

Spend Category ancestry is the current Spend Category tree captured and frozen once per LEDGER actuals snapshot. A Budget Position recomputes against the current hierarchy under a newly cited snapshot while the bound Budget Plan Revision stays unchanged, which is the semantic already resolved by OQ-BUDGET-8 and validated as A4. Determinism holds within one cited snapshot rather than across time.

CalculationSchemaVersion advances from `budget-position-v1` to `budget-position-v2`. The public BUDGET contract version stays 1.0 because the added result fields are additive, but ancestor row totals change meaning under the same field names, so the calculation schema version is the compatibility signal a consumer must branch on.

Calculator integrity gains one ancestry validation that mirrors the LEDGER ActualsCalculator invariant: for a categorized member the ancestry is non-empty, its final element equals the member Spend Category identifier, its elements are distinct, and every element resolves in the known Spend Category evidence set; for an uncategorized member the ancestry is empty. Any violation returns the stable integrity failure with no partial result. All new sums use checked Int64 arithmetic, and the existing assertion that bucket subtotals reconcile to the membership total stays unchanged as the exactly-once proof.

Spend Category lifecycle never changes resolution: an archived ancestor that carries an entry still governs, consistent with the existing rule that a Budget Actual bucket ignores active and archived lifecycle. Negative refund-heavy Budget Actuals resolve identically and stay signed without clamping or reclassification. A flat taxonomy is provably unchanged because a root Spend Category has ancestry equal to a single self element, so the scan yields either that entry or Unbudgeted Spend, producing values identical to the `budget-position-v1` result for the same inputs.


## Rationale

This reverses the OQ-BUDGET-10 resolution recorded against DD-BUDGET-EXACT-POSITION-CALCULATION, which chose exact-identity entries and stated that there is no subtree inheritance. That resolution named one specific hazard as its reason: overlapping parent and descendant entries could double count planned and actual totals. The nearest-entry scan plus the direct-versus-descendant partition removes that hazard mechanically rather than by prohibition, because resolution returns exactly one governing entry per Budget Actual and the row partition sums to the row total. The original fear is answered, so the original prohibition is no longer the cheapest way to stay exact.

The scan direction is the whole design. LEDGER already computes and freezes per-transaction ancestry into every actuals snapshot row, and BUDGET already receives it and discards it in the contract mapper. Nearest-entry resolution is therefore a reverse index scan over an array already in hand: no LEDGER change, no second query, no persisted derived state, no new snapshot semantics, and no change to the one-complete-snapshot rule that DD-BUDGET-EXACT-POSITION-CALCULATION established.

Keeping the calculator pure keeps the new rule property-testable. Resolution is a total function from one member plus one entry index to one outcome, so exactly-once counting is an assertion over arbitrary trees rather than an integration concern.

Rejected alternative A, freeze ancestry at classification time so a historical Budget Position never re-lenses: rejected because it requires a LEDGER storage column, new write-path invariants, and a migration, and because it contradicts OQ-BUDGET-8 and A4, which already resolved that a Budget Position recomputes current corrected actuals from a cited snapshot. Reversing that would make BUDGET the only consumer that pins historical LEDGER truth while owning no snapshot storage.

Rejected alternative B, issue one LEDGER actuals query per Category Budget Entry using the existing categoryScope subtree filter: rejected because nested entries return overlapping membership, so the same Budget Actual appears in multiple responses and the exactly-once guarantee would have to be reconstructed by subtracting descendant results. It also breaks the single-complete-snapshot rule by fanning one position across many snapshots with independent expiry.

Rejected alternative C, gate the new rule behind a request flag so exact-identity behavior remains selectable: rejected because a flat taxonomy is already unchanged under the new rule, so the flag would protect nothing while doubling the calculator paths and the property-test matrix for a single-owner local product.
