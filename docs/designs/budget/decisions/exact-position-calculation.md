## Description

Produce deterministic exact raw Budget Position values without double counting, hidden omissions, interpretation, or durable derived state.

## Decision

Bind one immutable Budget Plan Revision before calling LEDGER and reject an explicit revision that does not belong to the supplied period/currency. Materialize one complete compatible actuals snapshot in memory and pass both to a concrete pure BudgetPositionCalculator. Use Int64 ZAR minor units and checked addition, subtraction, and magnitude operations; overflow returns a stable integrity failure with no partial result. Assign every Budget Actual exactly once to Budgeted, ZeroBudget, Unbudgeted, or Uncategorized; a non-null assigned category omitted from the plan is Unbudgeted regardless of current active/archived lifecycle. Sort category IDs ascending and place Uncategorized last. Calculate exact totals and mutually exclusive Remaining or Over values. Persist no position, actual, cursor, report, or consumer state.

## Rationale

A pure calculator is the smallest deep boundary that makes all arithmetic and state distinctions property-testable without storage. SQL aggregation in either store would either duplicate LEDGER semantics or cross the private boundary. Persisted positions would become stale after corrections and confuse BUDGET with INSIGHTS report ownership.

## Alternatives

A: query BUDGET and LEDGER tables in joined SQL, rejected because stores and ownership are separate. B: persist monthly materialized positions, rejected as stale derived history. C: pure in-memory calculation over a cited complete snapshot, chosen.

## Consequences

Unbudgeted and Uncategorized values carry actual only; planned, Remaining, and Over are not applicable. Negative refund-heavy actuals are preserved. A period with no Budget Plan returns the explicit No Budget Plan state and a plan with no Active revision returns the explicit No Active Budget Plan Revision state, each before a LEDGER call. Any pagination or reconciliation failure returns no partial totals. The calculation schema version becomes provenance and compatibility metadata.
