**Status Notes:** Accepted. Store is BUDGET-owned and never read by other modules. **Ref Code:** DD-BUDGET-STATE-STORE

## Description

Persist plan intent, lifecycle, and replay outcomes without coupling them to Durable Ledger State or report retention.

## Decision

Use one owner-only budget.db under the Tally data root with Microsoft.Data.Sqlite, snake_case tables, foreign keys, WAL, synchronous FULL, bounded busy handling, PRAGMA user_version migrations, explicit BEGIN IMMEDIATE writer transactions, and one-writer constraints. Store plan, revision, entry, lifecycle, Active pointer, and idempotency metadata only. Do not persist LEDGER actual members, cursors, calculated positions, reports, or consumer state.

## Rationale

Sharing Ledger storage violates the public boundary and couples plan retention to financial facts. JSON files make atomic activation, one-Active enforcement, revision allocation, and replay recovery fragile. EF and a hosted database add layers and infrastructure without a second provider or request server. Raw SQLite matches established Tally storage and makes invariants directly testable.

## Alternatives

A: store plans in LEDGER, rejected as forbidden ownership coupling. B: canonical JSON files, rejected for multi-row atomicity and concurrency. C: EF/PostgreSQL, rejected by the self-contained local boundary. D: separate raw SQLite, chosen.

## Consequences

BudgetStateStore and migrations remain concrete. Real temporary SQLite is required in integration tests. The data root and directories use 0700 and database, WAL, SHM, lock, and recognized temporary files use 0600 where supported. Host volume protection remains an external deployment gate; no custom encryption is claimed.
