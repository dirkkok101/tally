# Compute period eligibility from host TimeProvider

**Status:** accepted
**Status Notes:** Accepted. One trusted date value is captured before local mutation and reused inside the transaction.
**Ref Code:** DD-BUDGET-TRUSTED-PERIOD-TIME

## Description

Make Current, Future, and Closed boundaries deterministic and immune to caller time, locale, and timestamp ambiguity.

## Decision

Require explicit year and month in every period-scoped request. Construct a start-inclusive and next-month-start-exclusive DateOnly interval. Capture one trusted host current calendar date from TimeProvider at operation start and use it for every eligibility check and transaction recheck. Do not accept caller current date, time zone, locale, or timestamp and do not persist period state as authority.

## Rationale

Caller time permits reopening or closing periods by crafted input, while persisted state becomes stale merely because the calendar advances. One captured host date makes the operation internally consistent and directly testable through the framework TimeProvider.

## Alternatives

A: caller-supplied now, rejected as untrusted and locale-sensitive. B: persist and schedule period closure, rejected because it adds background work and stale state. C: derive state from explicit boundaries and host TimeProvider on each operation, chosen.

## Consequences

Current, Future, and Closed are closed enums on results. Draft and activation commands reject Closed periods. Reads remain available. Tests substitute TimeProvider directly; no custom IClock is created and no scheduler is required.
