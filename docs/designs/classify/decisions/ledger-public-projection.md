# Use purpose-scoped classification projections on the public Ledger actuals contract

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** accepted
**Ref Code:** DD-CLASSIFY-LEDGER-PUBLIC-PROJECTION

## Description

Acquire complete eligible evaluation inputs and exact current apply-preflight state, including already-categorized corrections, without private Ledger reads or duplicated relationship semantics.

## Decision

Extend the next compatible ledger.actuals.query contract with a closed purpose of evaluation or apply_preflight and itemProjection classification_v1. Evaluation fixes categorizationState to requires_independent_decision. Apply preflight requires a bounded transactionIds selection and returns every selected transaction with Ledger-owned assignable, correctable, or ineligible mutation state plus current allocation identity and revisions, including already-categorized transactions. The first page returns snapshot and projection versions, store generation, expiry, category identity lifecycle fingerprint, active category catalogue, and ordered minimal classification items. Assignment asserts no active allocation; correction carries the expected active allocation identity and projection revisions so Ledger can reject drift atomically. Invoke projection and mutation operations through the concrete shared LedgerContractClient and released operation executor only.

## Rationale

One public projection family preserves stable ordering and Ledger-owned categorization, transfer, refund, relationship, allocation, and lifecycle truth, while evaluation eligibility and apply preflight have different membership. A requires-independent-decision query cannot preflight explicit corrections because those rows are already categorized. Purpose-scoped requests make the distinction closed and discoverable. Current allocation and revision preconditions close the race between preview, all-item preflight, and each Ledger write. Direct SQL or handlers violate the boundary; re-inferring eligibility duplicates finance semantics. Spike result: on 2026-07-31 installed Tally 0.3.2 and current main expose actuals, transaction detail, categories, and idempotent category mutations but do not publish classification_v1 or revision preconditions, so PLAN-CLASSIFY-RULEBOOK-V1 must release and prove this LEDGER-owned extension first.

## Alternatives

Rejected direct SQL, handlers, or private Ledger access because they bypass the released contract. Rejected re-inferring categorization, transfer, refund, allocation, or lifecycle eligibility in CLASSIFY because that duplicates Ledger-owned semantics. Rejected a classifier-specific private query because it cannot be discovered or compatibility-tested. Rejected one undifferentiated actuals filter because evaluation membership excludes already-categorized corrections that apply preflight must inspect.
