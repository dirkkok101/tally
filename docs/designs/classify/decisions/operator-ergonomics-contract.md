## Description

Defines the additive public surface and compatibility boundary for bounded CLASSIFY operator ergonomics.

## Decision

Add classify.outcome.list, classify.rule.list, classify.rule-set.active.get, classify.corpus.build, and classify.unresolved.report under contract version 1.0. Keep all twelve 0.3.3 request/result/error schemas compatible. Do not extend classify.status or classify.apply.preview: outcome.list composes with the existing selected_outcomes preview mode and its 200-outcome maximum. The resulting published inventory is 105 total operations and 17 CLASSIFY operations. All five operations use the existing typed envelope, source-generated JSON, operation registry, module handler composition, exit-code mapping, idempotency conventions, and metadata-only diagnostics.

## Rationale

Separate operations keep mutability, limits, privacy, and lifecycle semantics inspectable. A status extension would alter a strict released result shape, and a preview extension is unnecessary because explicit outcome IDs already provide the required batch contract.

## Alternatives

Change classify.status; rejected to preserve its released schema. Add apply-all or preview-by-filter; rejected because it weakens explicit selection and broadApplyAllowed=false. Use one generic discovery operation; rejected because rule, outcome, corpus, and unresolved-report authority differ.

## Consequences

The operation registry and contract inventory gain five additive entries. Existing clients remain valid. Rollback removes only the five new descriptors/handlers before release or restores the prior binary after release; durable engine state remains readable by 0.3.3, while a corpus file written by the new builder remains an ordinary private validation corpus.
