# Eight explicit workflow operations from one registry

**Ref Code:** DD-INGEST-CLI-OPERATION-CONTRACT

## Description

Define the smallest public surface that still makes every dangerous state transition visible.

## Decision

Expose ingest.preview, ingest.inspect, ingest.approve, ingest.commit, ingest.resume, ingest.status, ingest.abandon, and ingest.cleanup as versioned typed operations under tally ingest. One explicitly registered descriptor registry generates dispatch, help, machine schemas, compatibility metadata, limits, stable errors, and skill content. Complex input uses explicit stdin or file JSON; sourcePath is permitted only inside that private input. Each invocation emits exactly one business envelope.

## Rationale

The explicit surface minimizes caller knowledge and is the complete test boundary. A three-entry preview/act/status surface hides multiple transition schemas behind an action discriminator. Generic run/import/save/delete operations weaken discovery and make invalid states easy. Separate handwritten help, schema, and dispatch would drift. This adapts DD-LEDGER-CLI-OPERATION-CONTRACT and ADR-CORE-0010/0025 to INGEST.

## Alternatives

A: preview plus generic act plus status, rejected because callers still need every hidden transition invariant. B: generic run/import/save/delete, rejected because schemas and lifecycle semantics become ambiguous. C: eight explicit operations from one registry, chosen.

## Consequences

Operation IDs, schemas, limits, errors, exits, and state-transition meanings become compatibility commitments. New operations require additive versioning; unknown fields and unsupported versions fail before source processing or mutation.
