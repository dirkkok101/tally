# Per-batch locked idempotent candidate saga

**Ref Code:** DD-INGEST-COMMIT-RECOVERY

## Description

Close every cross-store crash window during candidate-granular commit.

## Decision

Commit and resume acquire one owner-only per-batch OS lock. For each frozen candidate in deterministic order, INGEST first durably records an attempting state and exact LEDGER request/key, then invokes the public LEDGER operation outside the INGEST transaction. An accepted or Exact Duplicate result is terminal only after its canonical transaction reference and immutable facts validate through the public get operation. A conflicted or rejected result is terminal only after its complete structured reference-free outcome is durably recorded. An unresolved result remains non-terminal. INGEST durably records every Terminal Candidate Outcome before advancing. Process loss releases the OS lock. Resume treats attempting as unresolved and replays the exact request/key; it skips reference-bearing terminal candidates only after their canonical reference remains structurally valid and skips reference-free conflicted or rejected candidates only from their complete durable outcome. Conflicts, compatibility failures, receipt-write failures, unresolved outcomes, and unsafe results stop continuation.

## Rationale

Holding an INGEST SQLite transaction across a LEDGER call would create long locks without atomicity. An in-memory cursor loses the recovery frontier. Batch-atomic import is impossible across two stores and conflicts with the accepted PRD. The stable LEDGER idempotency record makes the uncertain commit-before-receipt window replay-safe, while the per-batch OS lock prevents concurrent callers from racing the same saga.

## Alternatives

A: whole-batch distributed transaction, unavailable across separate stores. B: hold an INGEST SQLite transaction across each LEDGER call, rejected because it still is not atomic and creates long locks. C: in-memory progress, rejected because crash loses the frontier. D: per-batch lock plus durable attempting and terminal candidate states with idempotent replay, chosen.

## Consequences

Commit is intentionally a recoverable saga. Every candidate request and key freezes before its call, every Terminal Candidate Outcome persists before the next, and faults stop the frontier. Accepted and Exact Duplicate outcomes require a validated canonical reference; conflicted and rejected outcomes require a complete durable structured result and no fabricated reference; unresolved outcomes remain replayable. Lock acquisition, crash release, receipt write failure, reference-bearing replay, and reference-free terminal outcomes require direct integration coverage.
