# Two explicit adapters behind one narrow real seam

**Ref Code:** DD-INGEST-FORMAT-ADAPTERS

## Description

Separate fixture-qualified layout variability from the stable ingestion protocol without creating a generic parser platform.

## Decision

IStatementAdapter exposes immutable Descriptor, structural Probe(PdfDocumentEvidence), and Extract(PdfDocumentEvidence, exact released AccountDetail). Register only pdf-text-layout-a-v1 and pdf-text-layout-b-v1; exactly one probe must match. Each adapter owns its proven row boundaries, Source Row Identity, dates, balance-movement direction, exclusions, controls, and FinancialEvidence. Preview alone applies AccountDetail.AccountClass through FinancialNormalizer and then StatementReconciler. No wrapper/private account lookup, dynamic loading, rule language, OCR fallback, generic table parser, or cross-layout branch is allowed.

## Rationale

Two independently qualified adapters make this a real seam. Deleting it would smear detection and row semantics into preview orchestration. A single conditional parser grows into an untestable switch; regex or template configuration turns finance semantics into unreviewed data; per-bank child processes add lifecycle and distribution complexity. C7 and NG4 require the narrow registry.

## Alternatives

A: one conditional parser, rejected because detection and extraction drift together. B: user-authored regex or template rules, rejected because unreviewed configuration would own financial semantics. C: dynamic plugins or child processes, rejected as unsupported deployment and security complexity. D: two explicit adapters behind IStatementAdapter, chosen because two real implementations exist.

## Consequences

Every advertised variant needs representative golden fixtures, exclusive detection, deterministic bounded extraction, and versioned identity. A new format is a new adapter plus evidence. AccountDetail stays authoritative. metadataFingerprint is lowercase SHA-256 over canonical UTF-8 bytes: adapterVersion, one LF, then normalized layout-specific account-metadata fields joined by LF with no trailing LF. Each field is normalized with Unicode FormKC, invariant lowercase, and whitespace collapse before hashing. Layout A reconstructs visual lines in source page/line order, selects only lines containing the case-insensitive lexical marker account or card, removes monetary tokens, and rejects extraction if no metadata field remains. Layout A transaction rows are anchored by date, transaction amount, and running balance columns. Exactly one description-only visual line inside the row vertical midpoint band supplies source_text; zero candidates uses the typed fixed marker governed by DD-INGEST-SOURCE-DESCRIPTION-ABSENCE; multiple candidates reject. Original text evidence contains only anchored source lines and any assigned source description line. Layout B uses PdfPig DefaultPageSegmenter lines captured during bounded extraction plus source glyph baselines. Each page must have exactly one managed line containing the Date, Details, and Amount headers. A row is a managed line that starts with a yearless day and month and has a final signed monetary token. The period is the exactly two distinct full dates in content order. The row date must resolve to exactly one date in that period. Description glyphs are grouped at 0.1 PDF-point baseline tolerance, clipped between Date plus 0.33 of the Date-to-Details span and Details plus 0.75 of the Details-to-Amount span, and joined only when exactly one nonempty band is both within 5 PDF points of the managed row bottom and contained in normalized managed-row text. The final signed token is the movement. Opening and closing controls must each be unique managed lines and reconcile exactly. Layout B metadata fields are managed lines in page, block, and line order containing account or card after monetary-token removal; extraction rejects when no field remains. Paths, filenames, selected accountId, transaction rows, and financial values are excluded from metadataFingerprint. Any missing or duplicate header, period, row association, control, or metadata evidence rejects the variant.
