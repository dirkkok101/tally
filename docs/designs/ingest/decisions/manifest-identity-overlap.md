## Description

Define stable identities and the first-release duplicate boundary while OQ-INGEST-4 lacks cross-file evidence.

## Decision

Define the Exact Replay key as Source Fingerprint, selected account, adapter version, and LEDGER contract version; filename is excluded. Derive batchId from that key and manifestRevisionId from canonical source-generated JSON. Derive sourceRecordId from Source Fingerprint, stable structural position, raw record-evidence fingerprint, and the immutable-facts schema while excluding adapter and manifest versions. Derive candidateId from selected account, sourceRecordId, and immutable normalized facts while excluding manifest revision and compatible version metadata; derive the LEDGER idempotency key and statement-import source reference from candidateId. Preview checks the complete Exact Replay key first and returns a prior active or completed batch without reimport only when every key component matches. Changing the selected account changes candidateId and creates a new preview revision. A compatible adapter or LEDGER version change creates a new preview revision but retains sourceRecordId and candidateId only when the selected account, source row, and immutable financial facts are unchanged. The initial adapters claim no cross-file transaction identity. Identical tuples at distinct source positions remain distinct; a different source with an overlapping account/date window is blocked until identity-grade evidence resolves OQ-INGEST-4.

## Rationale

This fully satisfies safe v1 behavior without inventing identity. Tuple, fuzzy, and nearest-date matching can erase valid transactions and are disproven by the fixtures. Random IDs break deterministic replay. Persisting filenames as identity breaks rename safety and leaks private metadata. A content-addressed manifest binds approval and commit to exactly one reviewed meaning.

## Alternatives

A: random batch and candidate IDs, rejected because Exact Replay changes identity. B: filename or date-description-amount tuples, rejected because rename and duplicate tuples disprove uniqueness. C: fuzzy similarity suppression, rejected because false positives erase valid facts. D: content-addressed Exact Replay with overlap blocking, chosen.

## Consequences

Exact Replay is deterministic under any filename only when Source Fingerprint, selected account, adapter version, and LEDGER contract version all match. Account or version changes require a new preview rather than returning prior state. Changing the selected account changes candidateId; compatible version metadata remains excluded from sourceRecordId and candidateId so unchanged facts for the same selected account and source row do not become new candidates solely because compatible software changed. The initial adapters cannot auto-deduplicate across different sources; overlapping windows remain blocked until OQ-INGEST-4 gains identity-grade fixture evidence. Manifest canonicalization and hash compatibility remain explicitly versioned.
