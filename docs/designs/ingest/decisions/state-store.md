## Description

Persist review and recovery state without opening LEDGER storage or retaining source payloads longer than required.

## Decision

Use a separate owner-only ingest.db with immutable user_version migrations. V001 remains unchanged. V002 adds one durable append-only batch_error_event stream and one explicitly ephemeral status snapshot projection. Every workflow mutation that produces a stable expected failure appends the complete safe IngestError metadata in the same transaction as its batch, manifest, receipt, or candidate transition; the latest event is selected by per-batch sequence, so status never reconstructs category, mutation possibility, durable state, retry action, field, or safe message from a partial code. For list paging, the first status request opens BEGIN IMMEDIATE and materializes all retained metadata-only BatchStatusSummary rows in updatedAt-descending then batchId order into status_snapshot and status_snapshot_item, with a 15-minute expiry, contract version, store generation, exact total count, and ordinal. Later pages are read-only by snapshotId and ordinal. The cursor carries cursor version, contract version, snapshotId, next ordinal, page size, store generation, and expiry; every value is checked against the protected snapshot header, and unknown, expired, generation-mismatched, malformed, or out-of-range cursors fail closed. Snapshot creation may mutate only ephemeral query state and expired snapshots; StatusHandler never changes durable workflow, error, manifest, receipt, candidate, or Ledger state.

## Rationale

V001 error_code cannot produce the complete required guidance, and live offset or keyset paging cannot preserve rows that are concurrently updated or removed. Append-only error events make every returned field durable and attributable. The repository already proves the same bounded owner-only materialized snapshot pattern for LEDGER actuals. Materializing metadata-only status rows gives stable no-skip/no-duplicate pages without copying statement or financial payloads and without weakening the query boundary around durable business state.

## Alternatives

A: derive error metadata from candidate_receipt.error_code, rejected because category, safe message, mutation possibility, durable state, retry action, field, and batch-level failures are missing. B: page live ingest_batch rows by offset or keyset, rejected because concurrent updatedAt changes can skip or duplicate rows. C: encode the complete retained set in a stateless cursor, rejected because cursor size grows with history and cannot bind an ordinal to server state. D: materialize an owner-only metadata snapshot while keeping durable workflow state read-only, chosen.

## Consequences

A new V002 migration and migration-runner upgrade must land before status. All failure-producing mutation stores append BatchErrorEvent atomically. Status first pages may write only ephemeral snapshot rows and delete expired snapshots; detail lookup and later pages remain read-only. Snapshot rows contain no source path, statement row, description, amount, balance, full identifier, manifest, frozen request, or stack trace. Cleanup removes or invalidates snapshots before changing store generation.
