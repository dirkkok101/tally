# Statement Ingestion — Glossary

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

| Term | Definition | Source |
|---|---|---|
| Candidate Transaction | A normalized transaction proposal produced from one source row or source record. It retains provenance and validation state and is not canonical until accepted through the public LEDGER contract. |  |
| Exact Duplicate | A Candidate Transaction whose variant-defined Source Row Identity and source-derived financial facts match a prior canonical effect exactly. Only this identity-grade match may be suppressed automatically. Avoid: likely duplicate, fuzzy match. | discovery |
| Exact Replay | A new ingestion attempt whose Source Fingerprint, selected account, adapter version, and LEDGER contract version reproduce a prior batch identity exactly, regardless of filename, so the prior outcome can be returned without new canonical effects. Avoid: Exact Duplicate, which is a row-level financial identity claim. | design |
| Format Variant | A specific, detectable statement layout and encoding contract supported by one Source Adapter version; sharing a file extension does not make two layouts the same variant. |  |
| Import Batch | One immutable, reviewable ingestion attempt for a specific source artifact using a recorded adapter version and LEDGER contract version. It contains candidates and reconciliation evidence but does not itself imply LEDGER mutation. |  |
| Import Manifest | The immutable record of source fingerprint, adapter and contract versions, candidate mappings, validations, reconciliation evidence, and intended idempotency keys reviewed before commit. |  |
| Import Receipt | The durable machine-readable outcome of commit, mapping each candidate to its canonical LEDGER result or explicit unresolved state so an interrupted operation can resume safely. |  |
| Overlap Conflict | A candidate that resembles or shares a statement window with a prior transaction but lacks exact identity evidence, or reuses an identity with different facts. It blocks automatic commit. Avoid: duplicate, because that would overstate certainty. | discovery |
| Passive Parsing | Reading bounded document values without executing formulas, macros, scripts, hyperlinks, embedded objects, or remote fetches. Avoid: opening or rendering, which can imply active behavior. | discovery |
| Reconciliation Evidence | Source-provided controls such as row counts, debit and credit totals, opening and closing balances, page counts, or sequence markers used to prove extraction completeness for an import batch. It is not ongoing account balance reconciliation. |  |
| Reviewed Manifest Revision | The exact immutable Import Manifest version inspected and explicitly approved for commit. Any changed account mapping, eligibility decision, adapter version, or contract version requires a new revision and preview. Avoid: current batch when the revision is not named. | discovery |
| Source Adapter | A versioned local parser and normalizer for one evidenced bank format variant. It recognizes that variant explicitly and fails closed on unsupported layout changes. |  |
| Source Fingerprint | A deterministic identifier derived from the source artifact for exact-file replay detection. It is not, by itself, proof that two financial transactions are duplicates. |  |
| Source Row Identity | The provenance key that identifies a transaction-bearing record within its source context across retry and resume. Its components are format-specific and are established during discovery. |  |
| Terminal Candidate Outcome | A durable receipt result proving that one candidate was accepted into LEDGER, returned as an Exact Duplicate, or left blocked/rejected without mutation. A blocked or rejected transaction-bearing record keeps that manifest uncommittable and requires a new reviewed resolution. Avoid: processed, which does not state the financial effect. | discovery |
