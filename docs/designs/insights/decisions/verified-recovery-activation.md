## Description

Make backup and restore independently verifiable and fail closed across every SQLite and filesystem crash window.

## Decision

Backup first records an Attempting idempotency reservation with request hash and deterministic artifact identity, then creates a read-consistent private candidate that includes every prior terminal outcome but removes only the current non-terminal backup reservation. It verifies version, counts, links, payload fingerprints, idempotency, deletion state, permissions, and integrity, atomically publishes the artifact, then records the terminal receipt. Exact replay reconciles an already published verified artifact after a crash; completed failure removes its reservation. Verify is read-only and never changes Status. Restore verifies the source, builds a separate generation, applies compatible migrations, validates it, records the restore outcome in the candidate, revalidates, then under the exclusive writer lock checks the expected current fingerprint and atomically replaces CURRENT followed by directory fsync. The prior generation remains the recovery point.

## Rationale

Overwriting a live SQLite database creates WAL and partial-restore windows. A simple file copy cannot prove logical completeness. Generation directories and one atomic pointer make startup observe either the complete old state or the complete verified candidate and reuse the proven LEDGER recovery shape.

## Alternatives

A: restore over the live database, rejected because failure can destroy the authoritative store. B: rename individual database and WAL files, rejected because multi-file crash windows remain. C: verified generation plus atomic CURRENT activation, chosen.

## Consequences

Backup, candidate, pointer, lock, and prior-generation artifacts are recognized owner-only files. Fault tests cover reservation, candidate creation, removal of the current non-outcome reservation, artifact publication, terminal receipt, migration, verification, expected-current drift, pointer replacement, and fsync. A successful Backup or Restore stores its own durable verification evidence for Status; standalone Verify returns evidence only and changes neither active state nor Status. Restore adds only the current recovery outcome to the restored business state before activation.
