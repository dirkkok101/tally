# Single full-amount refund relationships

## Description

Define refund eligibility, cardinality, replay, and history for the full-refund-only product model.

## Decision

A refund relationship may link exactly one active original outflow to exactly one active refund credit only when both transactions belong to the same active owned account, both use ZAR, the original amount is negative, the refund amount is positive, and their absolute minor-unit amounts are exactly equal. Each participant may have at most one active financial relationship, so a second active refund for the original is rejected by the existing active-role exclusivity contract. Partial, cumulative, and over-refund relationships are unsupported. Confirmation appends an immutable relationship and never rewrites either ordinary bank transaction; revoke or replace appends lifecycle history. A semantically identical replay returns the original effect, while changed input under a consumed Idempotency Identity conflicts.

## Rationale

Dirk corrected the product requirement on 2026-07-22: expected refunds are for the full original amount. The existing role-exclusivity trigger already enforces the resulting one-active-refund cardinality and should remain unchanged.

## Alternatives

Rejected: support multiple partial credits with cumulative amount tracking, because Tally does not support partial refunds. Rejected: weaken relationship-role exclusivity for refund originals, because that would permit duplicate active refunds and require a different storage contract. Rejected: mutate or negate the original transaction, because bank transactions remain immutable source facts.

## Consequences

Refund confirmation rejects both smaller partial credits and larger over-refunds with the stable refund-amount error. A second active refund or any transfer/refund role reuse returns the stable active-role conflict. Retired relationship history remains attributable and a later valid replacement must revalidate exact full-amount eligibility. Existing schema and exclusivity trigger require no migration.
