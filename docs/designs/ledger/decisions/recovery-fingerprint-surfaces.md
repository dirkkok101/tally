# Separate restore and evolution fingerprints

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Status:** accepted
**Ref Code:** DD-LEDGER-RECOVERY-FINGERPRINT-SURFACES

## Description

Public recovery callers need both the storage-evolution source fingerprint and the Durable Ledger normalized fingerprint; using one field for both makes restore activation impossible through the published CLI.

## Decision

Keep StorageStatusResult.currentFingerprint as the storage-evolution source fingerprint and add currentNormalizedFingerprint from the verified current-equivalent Durable Ledger report. restore.activate.expectedCurrentFingerprint consumes currentNormalizedFingerprint; storage.evolution.activate.expectedCurrentFingerprint continues to consume currentFingerprint.

## Rationale

The two fingerprints protect different invariants. A separately named additive field preserves the evolution contract while giving restore callers the exact compare-and-swap value validated under the activation lock.

## Alternatives

Rejected changing currentFingerprint to the normalized value because that breaks storage evolution. Rejected deriving the value from backup or restore.prepare because those idempotent mutations change current Durable Ledger State before activation. Rejected weakening restore activation to compare the storage source fingerprint because that would bypass the complete normalized-state verification contract.

## Consequences

The status schema exposes two explicit 64-character lowercase SHA-256 values. Native CLI tests must prove a status-derived currentNormalizedFingerprint permits valid restore activation, stale current and stale candidate remain distinct, and currentFingerprint retains storage-evolution behavior.
