# Financial Ledger — Glossary

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

| Term | Definition | Source |
|---|---|---|
| Archived Ledger Entity | An account or category retained for historical references but unavailable for ordinary new assignments or transactions. Avoid: deleted, erased, inactive history. | discovery |
| Budget Actual | The exact External Spend restricted by current Spend Category and Spend Pool assignment. Active linked refunds use their own Effective Date and offset the original current category and pool; transfers contribute zero. Results expose uncategorized and unassigned-pool amounts separately. BUDGET compares this Ledger-owned actual with planned amounts. | discovery |
| Canonical Transaction | Tally's durable representation of one current economic event on one owned account. Facts are immutable; an approved statement may replace an earlier agent-capture fact through attributable supersession so exactly one version remains active while all evidence and history stay inspectable. Avoid: one active row per source observation or in-place overwrite. | discovery |
| Cardholder Attribution | A stable owner-managed identity indicating the person or role attributed to use of a Payment Instrument or transaction when relevant. It is optional, provider-neutral, and independently correctable. Avoid: recipient, Tally application user, bank account owner, or automatic inference from description. | discovery |
| Category Assignment | The attributable active or historical relationship between one Canonical Transaction and zero or one Spend Category node. It is independent from account, Payment Instrument, Cardholder Attribution, Spend Pool, and Pool Assignment; current hierarchy roll-ups derive from the category node rather than creating extra assignments. Avoid: split category allocation or using category as funding ownership. | discovery |
| Durable Ledger State | All authoritative state required to preserve behavior after restart or recovery: storage metadata; accounts, payment instruments, cardholders, spend pools, and categories with lifecycle history; Canonical Transactions; Evidence Records and links; Reconciliation Decisions, states, scopes, and exceptions; transaction, allocation, attribution, transfer and refund history; and idempotency outcomes. Rebuildable cursors and caches are excluded. | discovery |
| Effective Date | The explicit calendar date used to include a Canonical Transaction in period queries under the accepted date policy. Avoid: import timestamp, current time, or a fabricated timezone conversion. | discovery |
| Evidence Kind | A closed provider-neutral purpose classification such as agent capture, statement row, receipt, external document, or owner assertion. It describes what the evidence represents, not which transport supplied it. Avoid: AgentMail, WhatsApp, bank brand, MIME type, or delivery channel as a domain kind. | discovery |
| Evidence Record | A durable provider-neutral observation supporting or questioning one economic event, with a stable identity, Evidence Kind, privacy-conscious metadata, opaque external reference, and replay identity. It may be unlinked while ambiguous and one Canonical Transaction may have many. Avoid: raw email, MIME part, statement document payload, or synonym for Canonical Transaction. | discovery |
| External Orchestrator | A local automation system that invokes versioned Tally public commands under the owner OS identity and consumes structured results. Hermes is the current deployment and owns provider transport, conversation, schedules, recipients, rendering, delivery, and retries. It is a supporting actor, not a human persona. Avoid: treating Hermes, AgentMail, WhatsApp, or delivery behavior as LEDGER semantics. | discovery |
| External Spend | An exact net-spend amount for a selected set: add the positive magnitudes of active outflows in the set that are not principal legs of active owned-account transfers, then subtract the magnitudes of active linked refund/reversal credits in the set. Separately recorded fees and unlinked cash withdrawals remain included; unrelated inflows are excluded. A period can be negative when in-period refunds exceed in-period outflows. Avoid: raw signed account movement or every negative transaction. | prd |
| Idempotency Identity | A caller-visible stable identity for one intended public Ledger mutation. Same-operation, same-contract, semantically identical reuse yields the original result; reuse for another operation/version or a materially different request fails without mutation. Validation failures do not consume it. Avoid: fuzzy duplicate key, bank-description match, or database row ID. | prd |
| Net Account Movement | The exact base-10 sum of Signed Account Amount values for selected Canonical Transactions. Positive means net improvement and negative means net deterioration in the owner economic position. It is distinct from External Spend and Budget Actual, which transform qualifying outflows to positive magnitudes, subtract linked refund magnitudes, and exclude unrelated inflows and owned-transfer principal. | prd |
| Opaque External Reference | A caller-supplied privacy-safe token used to correlate an Evidence Record with state outside Tally. Ledger compares it only under documented identity rules and does not parse provider semantics from it. Avoid: full card or account number, mailbox payload, recipient address, or provider cursor. | discovery |
| Owned Bank Account | A local record representing one of Dirk's accounts at a financial institution, identified without storing login credentials or an unmasked secret account number. |  |
| Payment Instrument | A stable privacy-safe identity for a card or other means used to execute a transaction, optionally associated with an owned account and Cardholder Attribution. It may affect matching or reporting but is not the account, cardholder, spend pool, or category. Avoid: full card number, provider-specific wording, or account alias. | discovery |
| Pool Assignment | The attributable current or historical relationship between one Canonical Transaction and one Spend Pool, or an explicit unassigned state. Corrections append history; transfers contribute zero and linked refunds follow the original current pool. Avoid: deriving pool silently from account, instrument, cardholder, merchant, or category. | discovery |
| Reconciliation Decision | An append-only attributable determination that statement evidence confirms an existing transaction, authoritatively corrects it through replacement, creates a statement-only outcome, remains ambiguous, is owner-confirmed or rejected, or supersedes an earlier decision. It records deterministic policy or explicit owner authority, reason, statement basis, and affected history. Avoid: mutable matched flags, row overwrite, or silent fuzzy guesses. | discovery |
| Reconciliation Exception | A structured review-needed outcome such as conflicting evidence, invalid candidate, recorded transaction absent from a completed statement scope, stale decision, or lifecycle conflict. It preserves scope and reason and never authorizes a guessed match. Avoid: generic error with no recoverable context. | discovery |
| Reconciliation State | The current observable outcome derived from reconciliation history: recorded unreconciled, statement reconciled, statement-only, recorded absent from an approved statement scope, ambiguous match, explicitly owner-confirmed match, or reconciliation exception. Avoid: transport acknowledgement, statement import status, or unscoped missing flag. | discovery |
| Signed Account Amount | The exact base-10 owner economic-position delta for an Owned Bank Account. Positive means an asset increases or a liability owed decreases; negative means an asset decreases or a liability owed increases. Avoid: unsigned spend, raw display debit/credit label, or binary floating-point value. | discovery |
| Source Provenance | Provider-neutral lineage explaining which Evidence Records and Reconciliation Decisions support a Canonical Transaction and how they changed over time. It is an assembled history, not one transport-specific source field. Avoid: mailbox message ID as domain identity, MIME payload, single provenance slot, or import method as proof of uniqueness. | discovery |
| Spend Category | A stable user-managed classification node in LEDGER's acyclic category hierarchy. A transaction has zero or one direct Category Assignment; exact and subtree queries roll that assignment through current ancestry without double counting. BUDGET may reference the stable node but owns plan semantics. |  |
| Spend Pool | A stable owner-managed funding or responsibility dimension used to separate actual spending, including company-paid discretionary or personal-expense spending from personal after-tax spending. It is independent from account, Payment Instrument, Cardholder Attribution, and Spend Category. Avoid: budget amount, bank account, category group, or cardholder. | discovery |
| Statement-only Transaction | A Canonical Transaction created from an approved statement row after no compatible prior transaction exists. It has statement evidence but no earlier notification or owner-capture evidence at creation. Avoid: duplicate import row or proof that no other evidence can arrive later. | discovery |
| Transfer Pair | Exactly two active equal-and-opposite principal transactions on distinct owned accounts, each participating in that one active transfer and in no active refund relationship. Both facts remain queryable while their principal contributes zero External Spend; separately recorded fees remain outside the pair. | prd |
| Uncategorized Spend | A transaction currently included in spend but not assigned to a spend category; it remains visible and reportable rather than being silently forced into a category. |  |
| Verified Ledger Backup | A point-in-time, version-identifiable, access-restricted artifact containing the complete Durable Ledger State, whose compatibility, integrity, per-entity counts, relationship/cardinality rules, idempotency outcomes, and exact derived totals can be checked independently without mutating the live Ledger. Avoid: unverified file copy or transaction-only export report. | prd |
