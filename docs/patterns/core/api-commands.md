# Command Pattern — NxGN Actions

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Ref Code:** PAT-CORE-API-COMMANDS

## Purpose

**AI Summary**: Commands are write operations that modify the database. Production command constructors use IDbContextFactory<ActionsDbContext> and every DbContext-backed command execution method accepts optional ActionsDbContext? dbContext after CancellationToken so commands can run independently or participate in a caller-owned transaction. Save commands use the upsert pattern, delete and lifecycle commands return CommandResult variants, expected domain failures return structured CommandError, and transactional audit rows receive the shared context.

## Shared Result Types

All non-save commands return `CommandResult` or `CommandResult<T>`. These types live in `Features/Shared/Results.cs`:

```csharp
/// <summary>
/// Structured error payload — maps directly to SendProblemAsync parameters.
/// </summary>
public readonly record struct CommandError(string Code, string Message, int StatusCode = 400);

/// <summary>
/// Result for commands that don't return data (delete, simple lifecycle).
/// </summary>
public record CommandResult
{
    public CommandError? Error { get; init; }
    public bool Succeeded => Error is null;

    public static readonly CommandResult Success = new();
    public static CommandResult Fail(string code, string message, int statusCode = 400)
        => new() { Error = new(code, message, statusCode) };
}

/// <summary>
/// Result for commands that return data (lifecycle with response DTO, action commands).
/// </summary>
public record CommandResult<T> : CommandResult
{
    public T? Value { get; init; }

    public static CommandResult<T> Ok(T value) => new() { Value = value };
    // Inherits Fail() from base — returns CommandResult<T> via covariance
    public new static CommandResult<T> Fail(string code, string message, int statusCode = 400)
        => new() { Error = new(code, message, statusCode) };
}
```

### Design Rationale

| Concern | How CommandResult addresses it |
|---------|-------------------------------|
| Single return type per command | Every command returns one type — no discriminated unions, no multi-path matching |
| No boolean flag ambiguity | `Succeeded` is derived from `Error is null` — single source of truth |
| No exceptions for expected outcomes | NotFound, protection violations, invalid state → `CommandResult.Fail(...)` |
| Self-documenting errors | `CommandError` carries Code, Message, and StatusCode — maps directly to RFC 7807 |
| Simple endpoint consumption | `if (!result.Succeeded)` → `SendProblemAsync(...)` — no `Match()` ceremony |

### Error Code Convention

Error codes follow the format `{MODULE}-{NNN}` where:
- `{MODULE}` matches the feature folder name in UPPER-SNAKE-CASE (e.g., `ACTION`, `WORKFLOW`, `COMPLIANCE-PROFILE`)
- `{NNN}` is a zero-padded sequential number within the module, starting at `001`

| Code | Meaning | HTTP Status |
|------|---------|-------------|
| `{MODULE}-001` | Entity not found | 404 |
| `{MODULE}-002` | Uniqueness conflict (slug, code) | 409 |
| `{MODULE}-003` | Protection violation (system entity) | 422 |
| `{MODULE}-004+` | Feature-specific business rules | 422 |

Reserve `001`–`003` for the standard error types above. Feature-specific errors start at `004`. Each command documents its error codes in a comment block:

```csharp
// Error codes:
// ACTION-001: Action not found (404)
// ACTION-002: Slug already exists (409)
// ACTION-003: Cannot modify protected action (422)
// ACTION-004: Action has active workflows — cannot deactivate (422)
```

Error codes must be unique within a module. They are used for programmatic error handling on the frontend and appear in RFC 7807 problem details responses.

### When to use exceptions vs CommandResult

| Scenario | Use |
|----------|-----|
| Entity not found | `CommandResult.Fail("ENTITY-001", "...", 404)` |
| Protection check (system entity) | `CommandResult.Fail("ENTITY-002", "...", 422)` |
| Invalid state transition | `CommandResult.Fail("ENTITY-003", "...", 422)` |
| Business rule violation | `CommandResult.Fail("ENTITY-004", "...", 422)` |
| Uniqueness conflict (slug/code) | `CommandResult.Fail("ENTITY-005", "...", 409)` |
| TOCTOU unique constraint race | `CommandResult.Fail(...)` inside `catch (DbUpdateException)` |
| Unhandled/unexpected failure | Let exception propagate — ProblemDetailsService handles it |

**Every expected domain outcome uses `CommandResult.Fail()`** — including save commands. The only exceptions that propagate are genuinely unexpected failures (database connectivity, serialization errors, etc.).

## Mapper vs Command Boundary

The EntityMapper is a **pure DTO-to-Entity transformer**. The Command owns **all business logic**. This boundary is non-negotiable — see [entity-mapper.md](entity-mapper.md) for the full mapper pattern.

**The mapper does:**
- Entity resolution (find by ID, business key fallback)
- Create vs update detection (`Guid.Empty` = create)
- DTO field to entity field mapping
- Audit fields (CreatedDate/CreatedById, UpdatedDate/UpdatedById)
- Translation handling (AddOrUpdateEntityTranslation via TranslationService)

**The command does (everything else):**
- Call the mapper, receive `EntityMapperResult<T>`
- `AddRange(result.NewItems)` for new entities
- Business rules: uniqueness checks, guards, permission checks
- Cross-entity operations: create related entities
- Child collection diffing (aggregate root management)
- `SaveChangesAsync` with TOCTOU catch on unique constraints
- Post-save side effects (Redis invalidation, audit logging)

### Standard Save Command Flow

```
1. var mapResult = entityMapper.MapAsync(dtoList, userId, requestLanguageId, defaultLanguageId, ct, db)
2. if empty result (no NewItems, no UpdatedItems) → return Fail(404)
3. if (isNew) → db.AddRange(mapResult.NewItems)
4. Business logic (uniqueness check → Fail(409), guards → Fail(422), cross-entity ops)
5. try { SaveChangesAsync } catch { TOCTOU → Fail(409) }
6. Post-save side effects (audit, cache invalidation)
7. return Ok(mapResult)
```

## Save Command (Primary Pattern)

The save command is the standard write pattern. A single command handles both insert and update, returns `CommandResult<EntityMapperResult<T>>` or a feature-specific command result, and follows the shared DbContext contract from ADR-CORE-0027.

```csharp
public class SaveActionCommand
{
    private readonly IDbContextFactory<ActionsDbContext>? dbContextFactory;
    private readonly ActionsDbContext? defaultDbContext;
    private readonly ActionEntityMapper entityMapper;

    public SaveActionCommand(
        IDbContextFactory<ActionsDbContext> dbContextFactory,
        ActionEntityMapper entityMapper)
    {
        this.dbContextFactory = dbContextFactory;
        this.entityMapper = entityMapper;
    }

    internal SaveActionCommand(ActionsDbContext dbContext, ActionEntityMapper entityMapper)
    {
        defaultDbContext = dbContext;
        this.entityMapper = entityMapper;
    }

    public async Task<CommandResult<EntityMapperResult<ActionEntity>>> ExecuteAsync(
        SaveActionRequest request,
        Guid userId,
        CancellationToken ct = default,
        ActionsDbContext? dbContext = null)
    {
        var sharedDbContext = dbContext ?? defaultDbContext;
        if (sharedDbContext is not null)
        {
            return await ExecuteWithDbContextAsync(
                request,
                userId,
                sharedDbContext,
                ownsTransaction: sharedDbContext.Database.CurrentTransaction is null,
                ct);
        }

        if (dbContextFactory is null)
        {
            throw new InvalidOperationException("A DbContext factory is required when no shared context is supplied.");
        }

        await using var strategyDbContext = await dbContextFactory.CreateDbContextAsync(ct);
        var strategy = strategyDbContext.Database.CreateExecutionStrategy();
        return await strategy.ExecuteAsync(async () =>
        {
            await using var ownedDbContext = await dbContextFactory.CreateDbContextAsync(ct);
            return await ExecuteWithDbContextAsync(
                request,
                userId,
                ownedDbContext,
                ownsTransaction: true,
                ct);
        });
    }
}
```

Commands that do not open explicit transactions may use `DbContextFactoryExtensions.ExecuteWithDbContextAsync` directly. Commands that open transactions use the explicit owned/shared branch so owned mode can run inside the EF execution strategy and shared mode can participate in the caller's current transaction.

```csharp
            new { id = entity.Id },
            new SaveActionResponse(entity.Id), cancellation: ct);
    else
        await Send.OkAsync(new SaveActionResponse(entity.Id), ct);
}
```

## Delete Command

Delete commands accept `Guid[] keys` for bulk deletion using `ExecuteDeleteAsync`. They return `CommandResult` — protection checks return `CommandResult.Fail(...)` instead of throwing. Explicit transactions prevent partial deletes. Like save and lifecycle commands, they accept an optional `ActionsDbContext? db = null` for transaction spanning.

```csharp
public class DeleteWorkflowCommand(IDbContextFactory<ActionsDbContext> dbContextFactory)
{
    public async Task<CommandResult> ExecuteAsync(
        Guid[] keys, CancellationToken ct = default, ActionsDbContext? db = null)
    {
        var shouldDisposeContext = db is null;
        db ??= await dbContextFactory.CreateDbContextAsync(ct);
        try
        {
            // Protection check — returns structured error
            var protectedWorkflows = await db.Workflows
                .AsNoTracking()
                .Where(w => keys.Contains(w.Id) && w.IsSystemProtected)
                .Select(w => w.Name)
                .ToListAsync(ct);

            if (protectedWorkflows.Count > 0)
                return CommandResult.Fail("WORKFLOW-001",
                    $"Cannot delete protected workflows: {string.Join(", ", protectedWorkflows)}", 422);

            // Explicit transaction — prevents partial deletes on failure
            await using var tx = await db.Database.BeginTransactionAsync(ct);

            await db.WorkflowSteps
                .Where(s => keys.Contains(s.WorkflowId))
                .ExecuteDeleteAsync(ct);

            await db.WorkflowTriggers
                .Where(t => keys.Contains(t.WorkflowId))
                .ExecuteDeleteAsync(ct);

            await db.Workflows
                .Where(w => keys.Contains(w.Id))
                .ExecuteDeleteAsync(ct);

            await tx.CommitAsync(ct);
            return CommandResult.Success;
        }
        finally
        {
            if (shouldDisposeContext)
                await db.DisposeAsync();
        }
    }
}
```

## Soft Delete Command

Entities implementing `ISoftDeletable` (ActionEntity, ActionEvidence, ActionConsultation) are never physically deleted. Delete commands set `IsDeleted`, `DeletedDate`, and `DeletedById` instead of calling `ExecuteDeleteAsync`. The EF global query filter (`HasQueryFilter(e => !e.IsDeleted)`) excludes them from normal queries.

```csharp
public class DeleteActionsCommand(IDbContextFactory<ActionsDbContext> dbContextFactory)
{
    public async Task<CommandResult> ExecuteAsync(
        Guid[] keys, Guid userId, CancellationToken ct = default, ActionsDbContext? db = null)
    {
        var shouldDisposeContext = db is null;
        db ??= await dbContextFactory.CreateDbContextAsync(ct);
        try
        {
            var actions = await db.Actions
                .Where(a => keys.Contains(a.Id))
                .ToListAsync(ct);

            if (actions.Count != keys.Length)
                return CommandResult.Fail("ACTION-001", "One or more actions not found.", 404);

            foreach (var action in actions)
            {
                action.IsDeleted = true;
                action.DeletedDate = DateTime.UtcNow;
                action.DeletedById = userId;
            }

            await db.SaveChangesAsync(ct);
            return CommandResult.Success;
        }
        finally
        {
            if (shouldDisposeContext)
                await db.DisposeAsync();
        }
    }
}
```

**Key differences from hard delete:**
- Loads entities (required to set `ISoftDeletable` fields) — no `ExecuteDeleteAsync`
- Uses `SaveChangesAsync` (audit interceptor records the change)
- No explicit transaction needed — single `SaveChangesAsync` is already atomic
- To query including soft-deleted records (admin restore, audit views), use `IgnoreQueryFilters()`

See ADR-0020 for when to use soft delete vs hard delete.

## Lifecycle / Action Commands

These handle domain-specific operations that don't fit the save/delete pattern. They use the optional `ActionsDbContext? db = null` parameter for transaction spanning and return `CommandResult` (no data) or `CommandResult<T>` (with data).

### Without Response Data (`CommandResult`)

```csharp
public class ActivateComplianceProfileCommand(
    IDbContextFactory<ActionsDbContext> dbContextFactory,
    ILogger<ActivateComplianceProfileCommand> logger)
{
    public async Task<CommandResult> ExecuteAsync(
        Guid profileId, Guid userId,
        CancellationToken ct, ActionsDbContext? db = null)
    {
        var shouldDisposeContext = db is null;
        db ??= await dbContextFactory.CreateDbContextAsync(ct);
        try
        {
            var profile = await db.ComplianceProfiles
                .FirstOrDefaultAsync(p => p.Id == profileId, ct);

            if (profile is null)
                return CommandResult.Fail("PROFILE-001", "Compliance profile not found.", 404);

            if (profile.Status != ComplianceProfileStatus.Draft)
                return CommandResult.Fail("PROFILE-002", "Profile is not in draft status.", 422);

            var now = DateTime.UtcNow;
            profile.Status = ComplianceProfileStatus.Active;
            profile.ActivatedAt = now;
            profile.UpdatedDate = now;
            profile.UpdatedById = userId;
            await db.SaveChangesAsync(ct);
            return CommandResult.Success;
        }
        finally
        {
            if (shouldDisposeContext)
                await db.DisposeAsync();
        }
    }
}
```

## DbContext Lifetime and Transaction Spanning

Commands use two DbContext modes:

1. Owned mode: the command creates a short-lived `ActionsDbContext` from `IDbContextFactory<ActionsDbContext>` and owns persistence, transaction, retry strategy, and disposal.
2. Shared mode: the caller passes `ActionsDbContext? dbContext` so multiple commands or queries can participate in one caller-owned context and transaction.

The public command constructor injects `IDbContextFactory<ActionsDbContext>`. Commands must not inject scoped `ActionsDbContext` directly. Tests may use an internal constructor with a provided context, but production registration stays factory-based.

Every DbContext-backed command accepts the optional context after the cancellation token:

```csharp
public Task<CommandResult<EntityMapperResult<WorkflowDefinition>>> ExecuteAsync(
    SaveWorkflowRequest request,
    Guid userId,
    Guid requestLanguageId,
    Guid defaultLanguageId,
    CancellationToken ct = default,
    ActionsDbContext? dbContext = null)
```

Owned mode must run explicit transactions through EF Core's execution strategy. Create a separate strategy context, then create the working context inside the retry delegate so retries do not reuse a failed DbContext. Shared mode must not create or dispose the context. If the caller already opened a transaction, the command participates in it; otherwise the command may open and commit its own transaction on the supplied context when it owns the operation boundary.

```csharp
    var shouldDisposeContext = db is null;
    db ??= await dbContextFactory.CreateDbContextAsync(ct);
    try

        // ... command logic ...
    }
    finally
```

## Common Mistakes

### Save command returns CommandResult wrapping EntityMapperResult

```csharp
// CORRECT: CommandResult<EntityMapperResult<T>> with explicit failure handling
var mapResult = await entityMapper.MapAsync(
    [request], userId, requestLanguageId, defaultLanguageId, ct, db);

    return CommandResult<EntityMapperResult<ActionEntity>>.Fail("ACTION-001", "Not found.", 404);
// ... business logic, uniqueness checks return Fail on violation ...

// WRONG: Raw EntityMapperResult with ThrowError for expected outcomes

return mapResult;

// WRONG: SaveResult with boolean flags

{
    return SaveResult.Success(entity.Id);  // No structured result
}
```

### Guid.Empty vs Guid?


### DI-registered EntityMapper vs extension method mappers

## Rules

### MUST

1. Use `IDbContextFactory<ActionsDbContext>` in production command constructors; never inject scoped `ActionsDbContext` directly in production services.
2. Accept `ActionsDbContext? dbContext = null` after `CancellationToken` on every DbContext-backed command execution method so callers can compose commands in a shared transaction.
3. Use a public `IDbContextFactory<ActionsDbContext>` constructor for production command DI; internal `ActionsDbContext` constructors are allowed only for focused tests.
4. In owned mode, create the working DbContext inside the EF execution-strategy delegate before beginning an explicit transaction.
5. In shared mode, use the supplied DbContext and participate in its current transaction when one exists; do not dispose caller-owned contexts.
6. Stage audit rows through `IAuditService.LogAsync(..., dbContext)` when the audit entry must commit or roll back with the aggregate mutation.
7. Use the save (upsert) pattern - determine create vs update by `dto.Id == Guid.Empty`.
8. Use DI-registered `EntityMapper` classes that return `EntityMapperResult<T>` for the mapping step in save commands.
9. Save commands return `CommandResult<EntityMapperResult<T>>` or a feature-specific `CommandResult<T>` - check `Succeeded` before accessing `Value`.
10. Delete commands return `CommandResult` - protection checks return `CommandResult.Fail(...)`.
11. Lifecycle/action commands return `CommandResult` or `CommandResult<T>` - expected errors return `Fail(...)`.
12. Check for empty mapper result on update (entity not found) - return `Fail(404)`.
13. Use `SaveRequest : EntityDTO` inheritance when the write shape matches the read DTO.
14. Call `AddRange`/`UpdateRange` on `EntityMapperResult` lists.
15. Wrap `SaveChangesAsync` in try/catch for expected TOCTOU unique/concurrency conflicts and return `Fail(409)`.
16. Use explicit transactions for multi-table deletes and aggregate lifecycle commands that write multiple rows.
17. Use `ExecuteDeleteAsync` for hard deletes - never load-and-delete with `RemoveRange`.
18. Use soft delete where ADR-CORE-0020 requires historical preservation.
19. Wrap non-transactional post-save side effects in individual try/catch blocks.
20. Use `Guid.CreateVersion7()` for new entity IDs.

### SHOULD

1. Validate referential integrity before save.
2. Check system protection before mutation.

### MUST NOT

1. Create separate Create/Update commands - use a single Save command.
2. Use static extension method mappers - use DI-registered `EntityMapper` classes.
3. Query data for display inside commands - use the Query pattern.
4. Publish events directly from commands unless a documented feature design requires transactional outbox semantics.
5. Write audit rows directly from commands - use `IAuditService` with the shared DbContext parameter when audit is transactional.
6. Use `SaveResult` with boolean flags - use `CommandResult` variants.
7. Use `OneOf<>` for any command return type - use `CommandResult` variants.
8. Throw exceptions for expected domain outcomes.
9. Use `Guid?` with null to signal create - use `Guid.Empty`.
10. Open a transaction outside EF's execution strategy in owned mode when retries are enabled.

### Direct DbContext constructor breaks transaction composition

Production commands must use IDbContextFactory and an optional shared context parameter; direct scoped DbContext injection prevents callers from composing commands in one transaction and bypasses the retry-safe owned-context pattern.

```csharp
public class SaveWorkflowCommand(ActionsDbContext dbContext, IAuditService auditService)
{
    public async Task<CommandResult> ExecuteAsync(SaveWorkflowRequest request, CancellationToken ct)
    {
        dbContext.WorkflowDefinitions.Add(Map(request));
        await dbContext.SaveChangesAsync(ct);

        // Audit uses another context and cannot roll back with the workflow save.
        await auditService.LogAsync("workflow_definition.created", "Workflow", "WorkflowDefinition", request.Id, request.Name, request, ct);
        return CommandResult.Success;
    }
}
```

### MUST

- Use `IDbContextFactory<ActionsDbContext>` in command constructors; never inject scoped `ActionsDbContext` directly in production services.

- Use soft delete (set `ISoftDeletable` fields + `SaveChangesAsync`) for ActionEntity, ActionEvidence, ActionConsultation — never physically delete these entities (ADR-0020)
