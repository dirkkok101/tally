# Service Registration Pattern — NXGN Actions API

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Ref Code:** PAT-CORE-API-SERVICE-REGISTRATION

## Purpose

**AI Summary**: How to register feature services (commands, queries, mappers) with DI. Each feature defines a static `Add{Feature}Services()` extension method in `Bootstrap/Features/`. A central `Services.cs` orchestrator chains all feature registrations. All services use `AddScoped`. Called from `Program.cs` via `builder.Services.AddServices()`.

## The Core Principle

> **Explicit DI registration, organized by feature.** No reflection scanning or auto-discovery for feature services (commands, queries, mappers). Each feature owns its DI registration. Note: EF configurations use `ApplyConfigurationsFromAssembly()` for auto-discovery — the "no scanning" rule applies to DI registration, not EF model configuration (see [EF Configuration](ef-configuration.md)).

## Per-Feature Extension Method

Each feature registers its services via a static extension method on `IServiceCollection`:

```csharp
// Bootstrap/Features/WorkflowsExtensions.cs
using Nxgn.Actions.Api.Features.Admin.Workflows.Shared.Commands;
using Nxgn.Actions.Api.Features.Admin.Workflows.Shared.Mappers;
using Nxgn.Actions.Api.Features.Admin.Workflows.Shared.Queries;

namespace Nxgn.Actions.Api.Bootstrap.Features;

public static class WorkflowsExtensions
{
    public static IServiceCollection AddWorkflowsServices(this IServiceCollection services)
    {
        // Commands
        services.AddScoped<SaveWorkflowCommand>();
        services.AddScoped<DeleteWorkflowCommand>();

        // Queries
        services.AddScoped<GetWorkflowQuery>();
        services.AddScoped<GetWorkflowsQuery>();
        services.AddScoped<GetWorkflowsCountQuery>();

        // Mappers
        services.AddScoped<WorkflowEntityMapper>();
        services.AddScoped<WorkflowDTOMapper>();

        return services;
    }
}
```

### Sections

Organize registrations by type within each method. Not all features need every section:

| Section | Contains | When Needed |
|---------|----------|-------------|
| **Commands** | SaveCommand, DeleteCommand, lifecycle commands | Every writable feature |
| **Queries** | GetQuery, GetGridListQuery, GetCountQuery, GetLookupQuery | Every readable feature |
| **Mappers** | EntityMapper, DTOMapper, DTOMapperDataContextService | Every feature with DTOs |
| **Services** | Business logic services (validation, workflow, translation) | Features with complex domain logic |

### Feature with DTOMapperDataContext

When a DTOMapper needs pre-loaded data from multiple sources, the `DTOMapperDataContextService` is a separate scoped registration:

```csharp
// Bootstrap/Features/ActionsExtensions.cs
public static IServiceCollection AddActionsServices(this IServiceCollection services)
{
    // Commands
    services.AddScoped<SaveActionCommand>();
    services.AddScoped<DeleteActionCommand>();

    // Queries
    services.AddScoped<GetActionQuery>();

    services.AddScoped<GetActionsCountQuery>();

    // Mappers
    services.AddScoped<ActionEntityMapper>();
    services.AddScoped<ActionDTOMapper>();
    services.AddScoped<ActionDTOMapperDataContextService>();

    return services;
}
```

### Feature with Sub-Features

When a parent feature has child features (e.g., Actions -> Evidence, Consultations), sub-feature commands/queries are registered in the parent's extension method since they live in the parent's `Shared/` folder:

```csharp
// Bootstrap/Features/ActionsExtensions.cs
public static IServiceCollection AddActionsServices(this IServiceCollection services)
{
    // Commands
    services.AddScoped<SaveActionCommand>();
    services.AddScoped<DeleteActionCommand>();
    services.AddScoped<UploadEvidenceCommand>();        // Sub-feature command
    services.AddScoped<SaveConsultationCommand>();       // Sub-feature command

    // Queries
    services.AddScoped<GetActionQuery>();
    services.AddScoped<GetActionsQuery>();
    services.AddScoped<GetActionsCountQuery>();
    services.AddScoped<GetActionEvidenceQuery>();        // Sub-feature query

    // Mappers
    services.AddScoped<ActionEntityMapper>();
    services.AddScoped<ActionDTOMapper>();
    services.AddScoped<ActionDTOMapperDataContextService>();

    return services;
}
```

## Central Orchestrator: Services.cs

`Services.cs` chains all feature registrations into a single call. Organized by domain area:

```csharp
// Bootstrap/Services.cs
namespace Nxgn.Actions.Api.Bootstrap;

public static class Services
{
    public static IServiceCollection AddServices(this IServiceCollection services)
    {
        return services
            // Actions
            .AddActionsServices()

            // Administration
            .AddWorkflowsServices()
            .AddComplianceProfilesServices()
            .AddEscalationRulesServices()

            // System
            .AddLanguagesServices();
    }
}
```

**Rules:**
- Returns `services` for fluent chaining
- Comments group by domain area (not alphabetical)
- Every `Add{Feature}Services()` call has exactly one matching extension class
- New features add one line here and one new extension file

## Registration Rules

| Rule | Detail |
|------|--------|
| **Always `AddScoped`** | Aligns with `DbContext` scoped lifetime. Forces stateless design. Never `AddSingleton` for feature services. |
| **Explicit registration** | No reflection scanning (`services.Scan(...)`) for feature services. Explicit is auditable and debuggable. |
| **No constructor injection in bootstrap** | Registration is purely declarative — `services.AddScoped<T>()`. Resolution happens at request time by FastEndpoints. |
| **Return `services`** | Every extension method returns `IServiceCollection` for fluent chaining. |
| **Primary constructors** | All registered services use primary constructors — `public class SaveWorkflowCommand(IDbContextFactory<ActionsDbContext> dbContextFactory, ...)`. No `_field` naming. |

## What Goes Where

### In Bootstrap/Features/{Feature}Extensions.cs
- Commands (SaveCommand, DeleteCommand, lifecycle commands)
- Queries (Get, GridList, Count, Lookup)
- Mappers (EntityMapper, DTOMapper, DTOMapperDataContextService)
- Feature-specific services (validation, workflow)

### NOT in Bootstrap/Features/
- **Endpoints** — auto-discovered by FastEndpoints (no registration needed)
- **Validators** — auto-discovered by FastEndpoints (no registration needed)
- **DbContext** — registered in `Bootstrap/EntityFramework.cs`
- **HTTP pipeline** (auth, CORS, middleware) — registered in `Program.cs`

## Departures from Capstone

| Aspect | Capstone | Actions | Why |
|--------|----------|---------|-----|
| **Folder depth** | `Bootstrap/Features/{Area}/{Feature}Extensions.cs` | `Bootstrap/Features/{Feature}Extensions.cs` | Actions has fewer features; flat layout preferred |
| **Generic open types** | `services.AddScoped(typeof(SaveCommand<,>))` | Not used (no generic commands) | Actions features are concrete, not polymorphic |
| **DbContext registration** | `AddDbContextFactory` + `AddDbContextPool` (both) | `AddDbContextFactory` only | Actions uses factory pattern exclusively for scoped context creation |
| **Configuration style** | Static extension methods on `ModelBuilder` | `IEntityTypeConfiguration<T>` with `ApplyConfigurationsFromAssembly` | ADR-0018 — Actions chose per-entity configuration classes |
