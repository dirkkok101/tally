# Sub-Actions (Self-Referencing Hierarchy) — NXGN Actions

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Ref Code:** PAT-CORE-API-SUB-ACTIONS

## Purpose

**Scope**: This document describes the patterns for self-referencing entity hierarchies. Actions uses `ParentActionId` on `ActionEntity` to support sub-actions (child actions under a parent). This is a simplified version of Capstone's full TreeNode pattern — no TPH, no path materialization, no discriminators.

## Overview

`ActionEntity` has a self-referencing FK:

```csharp
public class ActionEntity : TrackedEntity, ITenantEntity, ISoftDeletable, IVersioned
{
    // ... other properties ...
    public Guid? ParentActionId { get; set; }
    public ActionEntity? ParentAction { get; set; }
}
```

This enables:
- Sub-actions nested under a parent action
- Guard conditions that check "all sub-actions are in terminal state"
- Hierarchical action screens (parent with child list)
- Recursive sub-action creation

## EF Configuration

```csharp
public class ActionEntityConfiguration : IEntityTypeConfiguration<ActionEntity>
{
    public void Configure(EntityTypeBuilder<ActionEntity> builder)
    {
        // ... other configuration ...

        // Self-reference
        builder.HasOne(e => e.ParentAction)
            .WithMany()
            .HasForeignKey(e => e.ParentActionId)
            .OnDelete(DeleteBehavior.Restrict);

        // Index for child lookups
        builder.HasIndex(e => new { e.TenantId, e.ParentActionId })
            .HasDatabaseName("ix_actions_tenant_parent");
    }
}
```

**Key conventions:**
- `OnDelete(DeleteBehavior.Restrict)` — deleting a parent is prevented while children exist. Children must be reassigned or deleted first (matches the [EF Configuration](ef-configuration.md) rule: `Restrict` for cross-aggregate references).
- `WithMany()` without a navigation collection — we don't load all children via the parent nav prop (use queries instead).
- Composite index on `(TenantId, ParentActionId)` for efficient child lookups under RLS.

## QueryParameters: Child Filtering

```csharp
public class ActionQueryParameters : PagedQueryParameters<ActionEntity>
{
    private Guid? parentId;
    private bool? rootsOnly;

    /// Filter to children of a specific parent
    public ActionQueryParameters WithParent(Guid parentId)
    {
        this.parentId = parentId;
        return this;
    }

    /// Filter to root actions only (no parent)
    public ActionQueryParameters WithRootsOnly()
    {
        rootsOnly = true;
        return this;
    }

    public override IQueryable<ActionEntity> ApplyFilters(IQueryable<ActionEntity> query)
    {
        query = base.ApplyFilters(query);

        if (parentId is not null)
            query = query.Where(a => a.ParentActionId == parentId);

        if (rootsOnly == true)
            query = query.Where(a => a.ParentActionId == null);

        return query;
    }

    public IQueryable<ActionEntity> IncludeRelations(IQueryable<ActionEntity> query)
    {
        return query
            .AsSplitQuery()
            .Include(a => a.ParentAction);
    }
}
```

## DTOMapper: Parent Reference

The parent is mapped as a `NamedDTO` (ID + display name), not a full nested DTO:

```csharp
public class ActionDTOMapper(
    TranslationService translationService,
    ILogger<ActionDTOMapper> logger)
{
    public ActionDTO Map(ActionEntity entity,
        Guid requestLanguageId, Guid defaultLanguageId)
    {
        var translation = translationService.GetEntityTranslation(
            entity, requestLanguageId, defaultLanguageId);

        return new ActionDTO
        {
            Id = entity.Id,
            ReferenceNumber = entity.ReferenceNumber,
            // Parent as NamedDTO (lightweight reference)
            ParentAction = entity.ParentAction is not null

                {
                    Id = entity.ParentAction.Id,
                    Name = entity.ParentAction.ReferenceNumber
```

## Guard Condition: Sub-Action Dependencies

The workflow engine evaluates a guard condition that checks all sub-actions are
in terminal state before allowing a parent action to transition:

```csharp
// In the guard evaluation chain
public async Task<GuardResult> EvaluateSubActionDependencies(
    ActionEntity action, ActionsDbContext db, CancellationToken ct)
{
    var openChildren = await db.Actions
        .Where(a => a.ParentActionId == action.Id)
        .Where(a => !a.IsDeleted)
        .Where(a => a.CurrentState.StateType != "Terminal")
        .CountAsync(ct);

    if (openChildren > 0)
        return GuardResult.Failed("SubActionDependencies",
            $"{openChildren} sub-action(s) are not in a terminal state");

    return GuardResult.Passed();
}
```

This guard is evaluated as part of the deterministic 9-guard chain documented in
the architecture.

## Descendant Queries

For operations that need all descendants (e.g., cascade soft-delete, impact
analysis), use stack-based traversal:

```csharp
public class GetActionDescendantIdsQuery(
    IDbContextFactory<ActionsDbContext> dbFactory)
{
    public async Task<HashSet<Guid>> ExecuteAsync(
        Guid parentActionId, CancellationToken ct)
    {
        await using var db = await dbFactory.CreateDbContextAsync(ct);

        // Load only Id + ParentActionId (lightweight)
        var pairs = await db.Actions
            .AsNoTracking()
            .Where(a => !a.IsDeleted)
            .Select(a => new { a.Id, a.ParentActionId })
            .ToListAsync(ct);

        // Build parent → children lookup
        var childrenByParent = pairs
            .Where(p => p.ParentActionId is not null)
            .GroupBy(p => p.ParentActionId!.Value)
            .ToDictionary(g => g.Key, g => g.Select(p => p.Id).ToList());

        // Stack-based traversal (no recursion)
        var result = new HashSet<Guid>();
        var stack = new Stack<Guid>();
        stack.Push(parentActionId);

        while (stack.Count > 0)
        {
            var current = stack.Pop();
            if (current != parentActionId)
                result.Add(current);

            if (childrenByParent.TryGetValue(current, out var children))
                foreach (var child in children)
                    stack.Push(child);
        }

        return result;
    }
}
```

**Key conventions:**
- Load only the columns needed (`Id`, `ParentActionId`) — not full entities
- Stack-based traversal — never recursion (avoids stack overflow on deep hierarchies)
- Exclude the root from results (descendants only, not self)
- Filter soft-deleted in the query

## Differences from Capstone TreeNode

| Concern | Capstone TreeNode | Actions Sub-Actions |
|---------|-------------------|---------------------|
| Inheritance | TPH with discriminator (OrgNode, DisciplineNode) | Single entity (ActionEntity) |
| Path | Materialized path per-translation (`"Root->Parent->Child"`) | No path — parent reference only |
| Path updates | Three-pass mapper (properties → parents → paths) | Single-pass (just set ParentActionId) |
| Depth | Arbitrary depth (org hierarchies) | Typically 1-2 levels (parent → sub-actions) |
| TreeNodeMap | Dual-index lookup (by ID and path) | Standard EntityMap (by ID only) |
| Tree service | TreeNodeService for path building, descendant traversal | Inline descendant query |
| Attribute values | Per-node custom attributes (TreeNodeAttributeValue) | None — actions use standard fields |

The simpler pattern is intentional — Actions' hierarchy is shallow (parent with
sub-actions), not a deep tree like Capstone's org structure.
