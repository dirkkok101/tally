# Configuration Ownership and E2E Data Pattern

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Ref Code:** PAT-CORE-CONFIGURATION-OWNERSHIP-E2E-DATA

## Purpose

Define when lookup/configuration data requires an admin module and how browser E2E data should be created for client setup scenarios.

## Classification

Every lookup used by an admin capture page must have an explicit owner. Immutable platform values may be compiled or seeded. Tenant-owned mutable values must be administered through a visible admin module and exposed to dependent pages through lookup endpoints. Derived lookups must come from the owning aggregate state, such as published workflow transitions from Workflow Configuration.

## Browser E2E Data

Browser E2E client setup scenarios should behave like a clean client onboarding run. They should create mutable tenant data through the frontend in commissioning order, then consume that data in downstream modules. Seed data may support authentication and immutable platform defaults, but successful module tests should not depend on editable client configuration being preloaded unless the scenario specifically validates seed immutability.

## Gap Handling

If a dependent module needs a lookup value that a tenant can reasonably change, and no admin module owns that value, treat it as a product/module gap rather than filling it with test seed data. Either add the missing admin module or record an explicit decision that the value is platform-owned and immutable.

## Owner Module Commissioning Order

Clean-system commissioning must happen through frontend admin modules in dependency order: access and roles, Action Type Management, Workflow Configuration, Deadline Types and Escalation Rules, RCA Method and Schema Management, then Compliance Profiles. Action Type and RCA Method data are tenant configuration when users can change them; their immutable platform templates may be seeded, but tenant-active rows must be created or activated through their owner modules. Downstream modules consume lookup contracts and show prerequisite empty states when owner data is missing.

## Shared Reference Lookups

A lookup endpoint can be owned by one admin module and still be required by another module's normal capture flow. In that case, the endpoint remains owned by the source module, but its authorization contract must include every consuming module permission that needs the lookup to complete an ordinary create or edit workflow. Tests must cover each allowed consuming permission so route/menu access and lookup access cannot drift apart.

## Platform-Owned Classification Examples

ADR-CORE-0029 classifies Priority, RiskLevel, SourceSystem, EvidenceType, and HierarchyOfControls as immutable platform-owned classifications. They may appear in dropdowns and lookup responses, but tenants do not own their value sets. Tenant setup configures behavior around them through owner modules such as Escalation Rules and Compliance Profiles. If custom risk scoring is required later, a Risk Matrix owner module must map tenant-specific rows back to the canonical RiskLevel bands instead of replacing the enum.

## Examples

### Frontend-created client configuration

The test creates mutable configuration through the same admin modules a tenant administrator uses, then consumes that data downstream.

```text
1. Create a custom deadline type through Escalation Deadline Types.
2. Create and publish a workflow through Workflow Configuration.
3. Configure a compliance profile that references the created deadline type and published transition.
```

## Counter-Examples

### Seed-only mutable lookup

This hides a missing admin surface and does not prove a client can configure the system.

```text
Seed an RCA method or action type directly in the database, then have Compliance consume it, while no admin module exists to create or change that value.
```

## Rules

### MUST

- Any lookup/configuration value that a tenant administrator can change must have an owning admin module or an explicit accepted decision stating why it is not user-configurable.
- Browser E2E client setup scenarios must create mutable tenant configuration through frontend admin flows before using that data in dependent modules.
- Seed data must be limited to immutable platform catalogues, Identity/application bootstrap, permissions, fixture personas, and scenarios that explicitly validate default/seed immutability.
- User-configurable lookup owner modules must expose a permissioned admin route, seeded translation keys, server-grid list, routed aggregate capture, and standard GET/SAVE/DELETE/grid-list/lookups endpoints.
- Action Type and RCA Method lookups are tenant configuration when clients can change them; downstream modules must consume the owning module lookup contract after frontend setup.
- Shared lookup endpoints used by another permission-gated admin capture flow must authorize the owning module permission and each consuming module permission required for normal create or edit workflows.

### MUST NOT

- Do not hide missing user-configurable admin modules by adding mutable lookup rows only to E2E seed data.
- Do not let downstream modules create, mutate, or silently seed another module's user-configurable catalogue inside their own save flow.
- Do not convert platform-owned classifications covered by ADR-CORE-0029 into tenant admin modules, mutable seed rows, or local per-module lookup tables unless ADR-CORE-0029 is superseded.

### SHOULD

- Dependent capture pages should show clear empty states when an owning module has not yet produced the prerequisite data, including which admin module must be configured next.
- Browser E2E commissioning should follow the documented dependency order: roles, Action Types, Workflows, Deadline/Escalation, RCA Methods, Compliance Profiles.
