# Canonical Feature Slice Naming — NXGN Actions

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Ref Code:** PAT-CORE-FEATURE-SLICE-NAMING

> Origin: 2026-04-21 ROLE/LANG execute review

## Purpose

Define the canonical naming vocabulary for API, BFF-proxy, and frontend feature slices so implementation, plans, and lex entities use the same verbs and nouns across the platform.

## Scope

This pattern applies to all feature slices in NxGN Actions:
- backend API slices
- BFF-style proxy slices over Identity
- Actions-owned backend functionality
- frontend feature services, page components, and route files
- lex plans, beads, feature areas, endpoint entities, and design notes

It exists because legacy names from one module must not silently become the convention for the next module.

## Canonical Vocabulary

API/backend canonical slice verbs:
- `Get` for a single entity or projection
- `GetGridList` for paged grid/list reads
- `GetLookup` or `GetLookupList` for lookup/dropdown reads, following the authoritative downstream/domain contract
- `Save` for upsert
- `Delete` for bulk delete
- `Assign` / `Unassign` for membership-style mutations when the domain uses those verbs
- `Get...Members` for membership lists
- `GetEffectivePermissions` / `GetEffectivePermissionsForUser` for enablement reads

Frontend canonical names:
- `{entity}.service.ts` with ergonomic methods like `getGridList()`, `getLookup()`, `save()`, `delete()`
- `{entity}-list.component.ts`, `{entity}-capture.component.ts`, `{entity}-membership.component.ts` for page shells
- `{feature}.routes.ts` for lazy route definitions

The server-side slice/class names and lex entities should use the canonical backend verbs even when the frontend service methods are shorter.

## Authoritative Source Rule

When a feature mirrors or proxies an authoritative downstream domain such as NxGN Identity, Actions must reuse that domain's canonical noun/verb vocabulary for the server-side slice names and lex references.

Examples:
- Identity-style `GetRolesGridListEndpoint` is authoritative for the roles grid slice; Actions should not invent `ListRolesEndpoint`
- Identity-style `AssignUserToRole` / `UnassignUsersFromRole` are authoritative for role membership mutations
- Identity-style `/permissions/lookup` is authoritative for permission catalogue routes; local docs must not drift to `/permissions`

A legacy local name in an older module is technical debt, not precedent.

## Good and Bad Examples

Good examples:
```text
Features/Admin/Roles/GetGridList/GetRolesGridListEndpoint.cs
Features/Admin/Roles/Get/GetRoleEndpoint.cs
Features/Admin/Roles/ListMembers/GetRoleMembersEndpoint.cs
Features/Admin/Roles/RemoveMember/UnassignUsersFromRoleEndpoint.cs
modules/admin/roles/role.service.ts        -> getGridList(), save(), getLookup()
modules/admin/roles/role-list.component.ts
modules/admin/roles/role-capture.component.ts
modules/admin/roles/role-membership.component.ts
modules/admin/roles/roles.routes.ts
```

Bad examples:
```text
Features/Admin/Roles/ListRoles/ListRolesEndpoint.cs
```
when the canonical slice is `GetGridList/GetRolesGridListEndpoint.cs`.

```text
EP-ROLE-PERMISSION-LOOKUP -> /api/v1/permissions
```
when the authoritative contract is `/api/v1/permissions/lookup`.

```text
Plan/bead says GetRolesGridList, implementation says ListRoles
```
This creates traceability drift and makes reviews unreliable.

## Rules

### MUST

- Use the canonical backend slice verbs `Get`, `GetGridList`, `GetLookup`/`GetLookupList`, `Save`, `Delete`, `Assign`, and `Unassign` unless the authoritative domain contract clearly dictates a different verb phrase.
- Keep lex entities, plans, beads, file paths, namespaces, classes, and tests aligned to the same canonical slice names.
- When proxying or mirroring Identity, reuse Identity's authoritative noun/verb vocabulary for the server-side slice names and contract-facing routes.

### MUST NOT

- Do not invent local synonyms such as `ListRoles` when the canonical slice is `GetRolesGridList`.
- Do not treat a legacy module's drift as precedent for new module implementation.

### SHOULD

- Frontend service methods may use ergonomic names like `getGridList()` and `getLookup()` while still mapping to canonical backend slice names.
- If naming drift is discovered while a module is still shallow, rename immediately rather than preserving the drift for compatibility.
