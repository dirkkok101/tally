# UI Translation Key Pattern

> Generated from the lex graph. Do not edit this file as source of truth; update graph entities and re-export.

**Ref Code:** PAT-CORE-WEB-TRANSLATIONS

> Origin: ADR-CORE-0026

## Purpose

Ensure every Actions Angular UI uses the shell-delivered translation key contract instead of hardcoded visible English.

## Scope and Ownership

Actions owns the product vocabulary for the Actions UI: translation key names, default English values, and the contract exposed from the Actions shell. Identity owns language definitions, language selection, translation persistence, and translation delivery. A module may consume translated entity values returned by APIs, but it must not invent local UI translation keys or treat entity i18n as coverage for static UI copy.

## Contract Flow

New UI copy starts in the shared contract. Add the key shape to Nxgn.Actions.Contracts/Shell/ActionsTranslationKeys.cs, register every key in Nxgn.Actions.Api/Features/Localization/ApplicationTranslationKeyRegistry.cs, seed the default value in Nxgn.Actions.Api/Features/Localization/ApplicationTranslationCatalogue.cs, mirror the shape in Nxgn.Actions.Web.Ui/src/app/core/shell/translation-key.models.ts, and update Nxgn.Actions.Web.Ui/src/app/testing/actions-translation-keys.ts. Components consume keys from TranslationKeyContractService after shell bootstrap.

## Planning Gate

Every new UI-facing module plan must include translation-key work as its own implementation gate before list, capture, route, or browser-test beads consume module copy. The minimum file-scoped task sequence is: ActionsTranslationKeys.cs contract shape, ApplicationTranslationKeyRegistry.cs key paths, ApplicationTranslationCatalogue.cs default English values, translation-key.models.ts Angular mirror, actions-translation-keys.ts test key fixture, module test translation values, and a fixture coverage assertion. If a module PRD or design mentions translated labels, validation messages, empty states, menu items, or admin UI copy, the plan must trace those requirements to this task sequence rather than relying on generic UI implementation beads.

## Component Usage

Angular components import TranslatePipe for template text and inject both TranslationKeyContractService and TranslateService for TypeScript-created text. Static template copy binds the key through translate. Code-created copy, including validation messages, toast text, confirmation dialogs, generated labels, and option labels, uses TranslateService. Computed strings that are cached in signals must depend on a translation revision signal sourced from onLangChange, onTranslationChange, and onDefaultLangChange so labels refresh when the active language changes.

## List and Grid Pages

Grid-list pages build nxgn.ui column definitions from translated headers and translated value formatters for static enum or status values. Column definitions must be recomputed when translations change. Server-side search, sort, and paging remain owned by nxgn.ui grid components and the module API contracts; Actions components provide translated page titles, action labels, empty/error text, and static cell labels.

## Capture and Edit Pages

Capture and edit pages use translation keys for headings, form labels, helper text, button text, validation messages, confirmation dialogs, loading text, and local option labels. API-provided lookup names may be displayed as data when the API contract returns translated values. Client-only enum fallbacks and generated defaults, such as New state 1 or Copy, must use translation keys with parameters instead of string concatenation.

## Testing and Seed Data

Tests seed the translation key contract and ngx-translate values before creating translated components. Test fixtures may contain English because they are explicit translation values, not UI implementation copy. Backend catalogue seed values are the other allowed place for default English UI copy. Tests should assert rendered translated labels where behavior depends on visible text and should keep key-contract coverage in sync with the C# and TypeScript models.

## Allowed Exceptions

The translation rule does not apply to technical identifiers, telemetry names, API route names, enum wire values, log messages intended only for operators, or user/domain data returned by APIs. When a value appears in the product UI as static chrome or explanatory copy, it is not an exception and must use the shell-delivered translation key contract.

## Examples

### Translated column definitions refresh with language changes

List pages compute nxgn.ui column headers from the shell key contract and TranslateService.

```typescript
private readonly i18n = inject(TranslationKeyContractService).keys;
private readonly translate = inject(TranslateService);
private readonly translationRevision = toSignal(
  merge(
    this.translate.onLangChange,
    this.translate.onTranslationChange,
    this.translate.onDefaultLangChange,
  ).pipe(startWith(null)),
  { initialValue: null },
);

protected readonly columnDefs = computed<ColDef[]>(() => {
  this.translationRevision();

  return [
    {
      field: "name",
      headerName: this.translate.instant(this.i18n.workflows.list.columns.name),
    },
  ];
});
```

### Template copy uses TranslatePipe

Templates bind visible copy through the key contract rather than literal English.

```html
<nxgn-grid-page-title [title]="i18n.workflows.list.title | translate" />

<label [for]="nameControl">
  {{ i18n.workflows.capture.fields.name | translate }}
</label>
```

## Counter-Examples

### Hardcoded UI copy drifts from the shell contract

Visible English in component code is not allowed because language changes cannot update it and the backend registry cannot validate it.

```typescript
protected readonly columnDefs = signal<ColDef[]>([
  { field: "name", headerName: "Name" },
]);

private showSavedToast(): void {
  this.toast.success("Workflow saved");
}
```

## Rules

### MUST

- Every new user-facing static UI string must be represented in ActionsTranslationKeys, ApplicationTranslationKeyRegistry, ApplicationTranslationCatalogue, the TypeScript translation-key model, and the Angular test translation fixture before the UI code is complete.
- Every UI-facing module implementation plan must include explicit file-scoped translation tasks for ActionsTranslationKeys.cs, ApplicationTranslationKeyRegistry.cs, ApplicationTranslationCatalogue.cs, translation-key.models.ts, actions-translation-keys.ts, module test translation values, and translation fixture coverage before UI component tasks consume module copy.
- Angular templates must render static copy through TranslatePipe using keys from TranslationKeyContractService.
- Component TypeScript must use TranslateService for code-created UI copy such as grid headers, enum labels, validation messages, confirmation dialogs, generated defaults, toast messages, and error fallbacks.
- Cached translated labels, including nxgn.ui grid column definitions and select option lists, must depend on translation change events so they refresh when the active language changes.

### MUST NOT

- Angular component templates, component TypeScript, and module-specific service stubs must not contain hardcoded visible English UI copy.
- Components must not concatenate translated and hardcoded words to generate labels; use parameterized translation keys instead.
- Modules must not bypass the shell-delivered Actions translation key contract with ad-hoc local key strings, local JSON files, or unregistered keys.

### SHOULD

- Feature keys should be namespaced under nxgn.actions.<feature> and grouped by page area, for example list, capture, fields, columns, statuses, confirmations, and errors.
- Components should display API-provided translated lookup and entity values as data, and only translate client-owned static labels and enum fallbacks.
