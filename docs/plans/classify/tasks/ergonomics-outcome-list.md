## Recipe

### Acceptance Checks

- evaluationId is required; all supplied outcome-kind, category, rule-version, stale-state, and transaction filters are ANDed; rows order by ordinal then transaction ID and pageSize is 1 through 500.
- Every item includes the DM-CLASSIFY-OUTCOME-PAGE selection/explanation fields and current category display/lifecycle evidence while excluding descriptions, amounts, normalized values, corpus paths, and authority claims.
- The query validates retained evaluation completeness/expiry, active rule-set membership, category lifecycle, Ledger generation/projection compatibility, cursor bindings, and total partition accounting before constructing the page.
- Missing, abandoned, expired, incomplete, archived-category, stale-generation, incompatible-projection, invalid-cursor, and integrity cases return the specified typed error, null result, and zero CLASSIFY/Ledger writes.
- A 146-row fixture with pageSize 500 returns all 146 IDs in one result and zero calls to outcome.get.

### Failure Criteria

- Do not persist a second outcome index, source description, amount, normalized token, or report artifact.
- Do not infer Ledger transfer/refund/void/allocation eligibility or return a partial page after a stale row.

### Expected Outputs

- ClassificationOutcomeDiscoveryStore, ListClassificationOutcomesQuery, and outcome-list mapper

### Constraints

- Ledger access is read-only through LedgerContractClient; live Tally data is never used by tests.
- The shipped classification_v1 contract is authoritative. A projection, query, lifecycle, or mutation-precondition gap blocks this CLASSIFY slice until an audited LEDGER-owned change and dependency exist.
