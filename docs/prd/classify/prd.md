## Problem Statement

CLASSIFY is shipped and correct, but an owner or Hermes agent cannot efficiently discover evaluation outcomes, inspect the active rulebook, assemble a fresh private validation corpus, or review repeated unresolved descriptions through bounded public operations. The concrete regression is that enumerating 146 outcomes with one classify.outcome.get process per row exceeded a five-minute orchestration timeout. The missing product capability is operator throughput and discoverability while preserving explicit selection, owner-only privacy, Ledger authority, and fail-closed mutation.

### OQ-CLASSIFY-6: How do category rename, archive/reactivation, transaction void/supersession, transfer/refund relationship changes, and stale snapshots invalidate suggestions or active rules?

- **Context:** Invalidation follows canonical identifiers and public lifecycle state; CLASSIFY never re-infers it from description text.
- **Decision:** Every outcome is bound to an Evaluation Fingerprint. Transaction void or supersession, transfer/refund relationship change affecting eligibility, allocation change, category archive/reactivation or identifier change, Ledger contract/store generation or snapshot change, normalization change, and rule-set change make the affected prior outcome stale. Category rename with the same stable active identifier does not alter the proposed identity but display data is refreshed. Stale outcomes cannot apply and must be re-evaluated.

### OQ-CLASSIFY-5: How should owner corrections propose, retire, narrow, or replace a Classification Rule without treating one corrected transaction as permission to generalize?

- **Context:** This prevents an erroneous correction or one-off exception from propagating automatically.
- **Decision:** A correction records feedback against the exact prior evaluation and rule version, then may propose the smallest retire, narrow, or replacement change with owner rationale. One correction never activates or broadens a rule. Every candidate is privately re-evaluated and activation remains explicit; Ledger correction history remains authoritative and unchanged.

### OQ-CLASSIFY-4: May an explicitly owner-approved exact rule batch-apply without per-transaction confirmation during an invoked run, and what evidence must the preview expose before apply?

- **Context:** This keeps batch value without granting a watcher or agent implicit mutation authority.
- **Decision:** V1 is suggestion-only by default. An exact rule may batch-apply only when the owner explicitly activated that rule for broad apply, explicitly invokes apply, and receives a current fingerprint-bound preview showing rule version, category, selected transaction count and identities, conflicts, exclusions, and no-suggestion totals. Apply revalidates all state, never includes conflicts, and returns one replay-safe LEDGER result per transaction.

- **Primary Actor:** P1

**Preconditions:**

**Scenario:**

## Glossary

| Term | Definition |
|------|------------|
| **Classification Apply Run** | An explicitly invoked, replay-safe attempt to submit an identified set of accepted suggestions or approved exact-rule matches through public LEDGER assignment/correction operations, returning one durable structured outcome per transaction. |
| **Classification Evaluation Run** | An explicitly invoked read-only evaluation of one snapshot-bound eligible transaction set using identified category, projection, normalization, and rule-set versions. It accounts for every eligible input and never mutates LEDGER. |
| **Classification Feedback** | An attributable owner action accepting, rejecting, or correcting a suggestion and optionally proposing a rule activation, narrowing, retirement, or replacement. Feedback does not automatically generalize or rewrite LEDGER history. |
| **Classification Rule** | A versioned owner-approved deterministic predicate over an allowed canonical transaction projection that proposes one active Spend Category and carries explicit scope, rationale, lifecycle, and provenance. A rule is not a LEDGER assignment. |
| **Classification Suggestion** | A read-only proposed Spend Category for one eligible transaction, accompanied by the exact rule/version and bounded Match Evidence that produced it. It cannot mutate LEDGER until an explicit apply operation succeeds. |
| **Eligible Classification Transaction** | An active canonical LEDGER transaction that requires an independent category decision under current categorization, transfer, refund, relationship, and lifecycle state. CLASSIFY discovers eligibility through public LEDGER queries and never infers those states from description text. |
| **Evaluation Fingerprint** | A deterministic integrity identity over the LEDGER contract and snapshot or store generation, category catalogue, classification projection, normalization, rule set, and when applicable private evidence source. A mismatch makes prior output stale. |
| **Match Evidence** | The structured, privacy-bounded explanation of which allowed normalized features satisfied a Classification Rule. It must be sufficient to review determinism without exposing unrelated transaction payloads or hidden model reasoning. |
| **Private Classification Evaluation Corpus** | Owner-only representative and held-out canonical examples with expected outcomes used to measure coverage, conflicts, drift, and incorrect-application canaries. Raw rows and financial payloads never enter Git or diagnostics. |
| **Rule Conflict** | The fail-closed outcome when more than one active rule can produce incompatible category decisions for the same transaction or when precedence is not explicitly valid. A conflict remains unapplied until resolved. |
| **Rule Set Version** | An immutable addressable collection of active Classification Rule versions evaluated together. Candidate, active, retired, and superseded lifecycle changes are explicit and attributable. |
| **Stale Classification Outcome** | A prior suggestion, no-suggestion, or conflict whose Evaluation Fingerprint no longer matches current transaction lifecycle or relationship state, category lifecycle, LEDGER contract or snapshot, normalization, or rule set. It cannot be applied and must be re-evaluated. |
