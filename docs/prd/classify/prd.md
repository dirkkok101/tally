## Problem Statement

Surface pain: transaction descriptions vary by bank and period, so assigning every transaction manually will not scale and inconsistent assignments weaken budget analysis. 5 Whys: Why classify? BUDGET and INSIGHTS need stable category membership, while LEDGER correctly keeps uncategorized spend explicit. Why is manual assignment insufficient? INGEST will increase the number and recurrence of canonical transactions, and the owner must repeatedly interpret noisy descriptions. Why not let an agent simply guess? Unrecorded guesses are inconsistent, cannot explain confidence, and do not reuse corrections safely. Why do corrections not solve the next transaction today? LEDGER preserves attributable assignments but CLASSIFY has no deterministic feedback contract that turns an owner decision into reusable evidence. Root problem: Tally lacks an auditable, local feedback loop that converts canonical transaction evidence and prior owner-approved decisions into deterministic category suggestions and explicit assignments without rewriting source facts or silently distorting actuals. Without CLASSIFY, the owner repeats the same judgement, uncategorized spend accumulates, and downstream budget and insight results remain incomplete. The sole Personal Finance Owner discovers a versioned CLASSIFY command through the AI Agent Host, evaluates uncategorized canonical transactions, reviews rule evidence or an explicit no-suggestion/conflict result, applies accepted decisions through public LEDGER operations, and uses later corrections to improve future rule proposals.

## Personas

### P1: Personal Finance Owner

- **Role:** Sole owner and decision-maker for household finances
- **Goals:** When reviewing or planning personal spending, I want one trustworthy view across all owned accounts, evidence sources, spend pools, and categories so I can delegate maintenance safely and know why each transaction is present.

- **Success Looks Like:** The owner can delegate daily capture and monthly reconciliation, review every ambiguous or missing match, and retrieve exact pool/category totals whose evidence and decision history are inspectable.

- **Usage Frequency:** daily

1. Given a transaction becomes void in public LEDGER state, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
2. Given a transaction is superseded in public LEDGER state, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
3. Given a transaction allocation changes in public LEDGER state, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
4. Given a transaction's transfer relationship changes in public LEDGER state, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
5. Given a transaction's refund or reversal relationship changes in public LEDGER state, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
6. Given a targeted category is archived, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
7. Given a targeted category is reactivated, when a prior outcome created before reactivation is inspected or applied, then CLASSIFY reports it stale and blocks apply.
8. Given a targeted category identity changes, when a prior outcome is inspected or applied, then CLASSIFY reports it stale and blocks apply.
9. Given a category rename that preserves the same active identifier, when a prior outcome is inspected, then its category identity remains valid and the current display name is returned.
10. Given the required LEDGER contract or classification projection version changes, when a prior outcome is inspected or applied, then CLASSIFY identifies that changed fingerprint dimension and blocks apply.
11. Given the LEDGER store generation changes, when a prior outcome is inspected or applied, then CLASSIFY identifies that changed fingerprint dimension and blocks apply.
12. Given the source LEDGER snapshot is invalid or expired, when a prior outcome is inspected or applied, then CLASSIFY identifies that changed fingerprint dimension and blocks apply.
13. Given the normalization version changes, when a prior outcome is inspected or applied, then CLASSIFY identifies that changed fingerprint dimension and blocks apply.
14. Given the active Rule Set Version changes, when a prior outcome is inspected or applied, then CLASSIFY identifies that changed fingerprint dimension and blocks apply.
15. Given a stale outcome, when the owner requests the permitted next operation, then CLASSIFY returns re-evaluate and does not return correction or apply.

### FR-CLASSIFY-RULE-LIFECYCLE: Manage versioned deterministic rules

- **Priority:** Critical
- **Description:** Create, inspect, activate, retire, and replace attributable immutable Classification Rule versions and Rule Set Versions. Implements G2, G4, and UC-CLASSIFY-004.
- **Rationale:** Reusable owner decisions remain safe only when rule scope and lifecycle are explicit, reviewable, and reversible.

**Acceptance Criteria:**

1. Given a supported predicate over schema-allowed fields and an active category identifier, when a rule draft is saved, then CLASSIFY records a new immutable draft version with owner, reason, scope, normalization version, and proposed category.
2. Given a rule draft is saved, when the operation completes, then no rule or Rule Set Version is activated and no LEDGER mutation occurs.
3. Given an unsupported field or predicate, when a rule draft is saved, then CLASSIFY returns stable field-level validation errors and creates no activatable version.
4. Given a category identifier is missing from the current catalogue, when a rule draft is saved, then CLASSIFY returns a stable category-not-found error and creates no activatable version.
5. Given a category identifier is archived in the current catalogue, when a rule draft is saved, then CLASSIFY returns a stable category-inactive error and creates no activatable version.
6. Given a draft whose required private validation passed, when the owner explicitly activates it, then CLASSIFY creates a new immutable active Rule Set Version containing the exact activated rule version.
7. Given an active rule, when the owner retires it with a reason, then CLASSIFY creates a new active Rule Set Version without that rule and retains the retired version for inspection.
8. Given an active rule that must be narrowed or replaced, when the owner activates a validated successor, then the successor references the prior version and the prior version becomes retired or superseded without in-place mutation.
9. Given a category rename that preserves the same active category identifier, when rules are inspected, then their category identity is unchanged and their display name resolves to the current catalogue name.
10. Given any owner decision, correction, or feedback event, when the event is recorded, then no rule version or Rule Set Version is activated automatically.
11. Given a draft entered through classify.rule.save, when it is retained, then its immutable rule version records rule_origin=owner_authored and no personal rule value is compiled, seeded, logged, or exported.
12. Given a draft originating from correction feedback, when it is retained, then its immutable rule version records rule_origin=feedback_derived and receives no validation, activation, broad-apply, or mutation authority from that origin.

### FR-CLASSIFY-RULE-VALIDATION: Validate candidate rule sets against private evidence

- **Priority:** Critical
- **Description:** Evaluate candidate normalization and Rule Set Versions against owner-only representative and temporal hold-out evidence before activation or broad apply. Implements G6 and UC-CLASSIFY-004.
- **Rationale:** A deterministic rule can still be consistently wrong; private held-out evidence is the activation safety gate.

**Acceptance Criteria:**

1. Given a candidate normalization or Rule Set Version and an owner-only corpus, when validation starts, then the run records the candidate, corpus, expected-outcome, category-catalogue, projection-contract, and normalization fingerprints.
2. Given a completed validation run, when its report is returned, then every corpus row is accounted for and aggregate totals report suggestions, no-suggestions, conflicts, stale rows, drift canaries, and incorrect-application canaries.
3. Given any missing or stale required fingerprint, when activation is attempted, then CLASSIFY rejects activation without changing the active Rule Set Version.
4. Given any incorrect-application canary, when activation is attempted, then CLASSIFY rejects activation without changing the active Rule Set Version.
5. Given any unexplained incompatible-category conflict in required evidence, when activation is attempted, then CLASSIFY rejects activation without changing the active Rule Set Version.
6. Given an unavailable private corpus, when an existing active rule set is evaluated, then CLASSIFY may use that unchanged active version.
7. Given an unavailable private corpus, when a new rule or normalization version is activated, then CLASSIFY rejects activation without changing the active Rule Set Version.
8. Given an unavailable private corpus, when broad-apply authorization is requested, then CLASSIFY rejects authorization before LEDGER mutation.
9. Given a validation report, when it is persisted or exported, then it contains corpus fingerprints and aggregate outcomes but no raw transaction description, normalized token, financial value, or expected-outcome row.
10. Given an owner-authored candidate rulebook, when its pre-authority gate runs, then every private row is accounted for exactly once, incorrect applications and unexplained incompatible conflicts are zero, coverage and no-suggestion totals are explicit, drift canaries and deterministic fingerprints are stable, and owner decision and time benefit are measured.
11. Given owner-authored safety passes but measured benefit is insufficient for broad authority, when activation or exact-rule broad apply is considered, then CLASSIFY requires an explicit product decision and does not invent a 50 percent benefit threshold.

## Glossary

| Term | Definition |
|------|------------|
| **Classification Apply Run** | An explicitly invoked, replay-safe attempt to submit an identified set of accepted suggestions or approved exact-rule matches through public LEDGER assignment/correction operations, returning one durable structured outcome per transaction. |
| **Classification Evaluation Run** | An explicitly invoked read-only evaluation of one snapshot-bound eligible transaction set using identified category, projection, normalization, and rule-set versions. It accounts for every eligible input and never mutates LEDGER. |
| **Classification Feedback** | An attributable owner action accepting, rejecting, or correcting a suggestion and optionally proposing a rule activation, narrowing, retirement, or replacement. Feedback does not automatically generalize or rewrite LEDGER history. |
| **Classification Rule** | A versioned owner-approved deterministic predicate over an allowed canonical transaction projection that proposes one active Spend Category and carries explicit scope, rationale, lifecycle, and provenance. A rule is not a LEDGER assignment. |
| **Classification Suggestion** | A read-only proposed Spend Category for one eligible transaction, accompanied by the exact rule/version and bounded Match Evidence that produced it. It cannot mutate LEDGER until an explicit apply operation succeeds. |
| **Eligible Classification Transaction** | An active canonical LEDGER transaction that requires an independent category decision under current categorization, transfer, refund, relationship, and lifecycle state. CLASSIFY discovers eligibility through public LEDGER queries and never infers those states from description text. |
| **Evaluation Fingerprint** | A deterministic integrity identity over the LEDGER contract and snapshot or store generation, category catalogue, classification projection, normalization, rule set, and when applicable private evidence source. A mismatch makes prior output stale. |
| **Match Evidence** | The structured, privacy-bounded explanation of which allowed normalized features satisfied a Classification Rule. It must be sufficient to review determinism without exposing unrelated transaction payloads or hidden model reasoning. |
| **Private Classification Evaluation Corpus** | Owner-only representative and held-out canonical examples with expected outcomes used to measure coverage, conflicts, drift, and incorrect-application canaries. Raw rows and financial payloads never enter Git or diagnostics. |
| **Rule Conflict** | The fail-closed outcome when more than one active rule can produce incompatible category decisions for the same transaction or when precedence is not explicitly valid. A conflict remains unapplied until resolved. |
| **Rule Set Version** | An immutable addressable collection of active Classification Rule versions evaluated together. Candidate, active, retired, and superseded lifecycle changes are explicit and attributable. |
| **Stale Classification Outcome** | A prior suggestion, no-suggestion, or conflict whose Evaluation Fingerprint no longer matches current transaction lifecycle or relationship state, category lifecycle, LEDGER contract or snapshot, normalization, or rule set. It cannot be applied and must be re-evaluated. |
