## Problem Statement

Manual entry cannot keep the three-account Financial Ledger complete, while the three real private PDF statements use two layouts and encode account class, amount sign, row dates, balances, and non-movement records differently. The 5 Whys chain is: manual entry is too slow for historical and recurring data; the files contain the needed scale; each layout encodes facts differently; ad hoc parsing can silently omit, duplicate, or misstate plausible rows; and every later classification, budget, and insight becomes untrustworthy when canonical facts are wrong. The root problem is the absence of a deterministic local statement-to-LEDGER import boundary that preserves source provenance, exposes ambiguity before mutation, reconciles every supported statement, and makes retries duplicate-safe. The desired journey is agent-first: the owner downloads a statement, an agent discovers INGEST operations, previews candidates and reconciliation evidence for an explicitly selected account, reviews an immutable manifest, explicitly commits accepted movements through public LEDGER commands, and receives a receipt proving every accepted, duplicate, excluded, blocked, and failed outcome.

### OQ-INGEST-4: What constitutes stable Source Row Identity across repeated files, overlapping statement windows, corrected statements, and files renamed by the owner?

- **Context:** Fixture evidence disproves tuple-only identity: no explicit source transaction ID is present and one statement repeats a date-description-amount tuple. Content fingerprint plus row ordinal handles exact-file replay, but overlapping and corrected statement behavior still requires representative fixtures and remains open.
- **Decision:** V1 claims no cross-file transaction identity. Exact source replay is automatic; any different source with an overlapping account and date window blocks. Future identity-grade evidence may reopen and supersede this rule, but it does not block the fail-closed v1 design.

### OQ-INGEST-9: How is a source file matched to a canonical account when the statement exposes only masked or unstable identifiers?

- **Context:** Define deterministic matching, explicit owner confirmation, and safe behavior when multiple accounts remain plausible.
- **Decision:** The caller must explicitly supply one active canonical LEDGER account identity for preview. Statement metadata validates that choice; missing, conflicting, multi-account, or ambiguous metadata blocks commit. INGEST never selects an account solely from a filename or masked identifier.

### UC-INGEST-001: Preview and qualify a local statement

- **Primary Actor:** P1
- **Trigger:** The Personal Finance Owner has downloaded a local bank statement for an owned account and wants to import it.
- **Depth Tier:** 3
- **Status:** draft

**Preconditions:**

A compatible Tally executable is available; the target LEDGER account exists and is active; the source is a readable owner-supplied local file; no adapter support is assumed from its extension alone.

**Scenario:**

1. The owner or delegated AI Agent Host discovers INGEST operations, supported Format Variants, limits, schemas, and errors. 2. The owner supplies the read-only source path and explicit canonical account identity. 3. INGEST fingerprints the source and detects one supported adapter/version without executing active content. 4. The adapter extracts normalization-ready FinancialEvidence and statement controls; preview applies the selected public AccountDetail.AccountClass through FinancialNormalizer and passes the normalized movements plus extracted controls to StatementReconciler. 5. INGEST accounts for non-transaction records, validations, duplicates, and Reconciliation Evidence. 6. INGEST freezes an immutable Import Manifest revision. 7. **Postconditions:**

No LEDGER mutation occurred; the source is unchanged; one owner-only manifest revision identifies every candidate, exclusion, validation, adapter/contract version, and reconciliation result.

**Failure Paths:**

- 2a. Source path is unreadable or changes during preview -> return a stable source failure and persist no committable manifest
- 2b. Statement metadata conflicts with the selected account -> block the batch without inferring another account
- 3a. No supported Format Variant is detected -> return unsupported-format and no mutation
- 3b. Password protection, scanning, active content, external references, or resource limits prevent passive bounded parsing -> fail closed
- 4a. A required amount, currency, date, description, source identity, or row boundary is ambiguous -> block the batch rather than guess

### FR-INGEST-APPROVED-BATCH-COMMIT: Commit approved candidates through public LEDGER operations

- **Priority:** Critical
- **Description:** Invoke only the discovered versioned LEDGER transaction contract for accepted candidates in an approved manifest using stable per-candidate idempotency identities. Implements G4 and UC-INGEST-003.
- **Rationale:** INGEST must not bypass canonical validation or own a second financial datastore contract.

**Acceptance Criteria:**

1. Given an approved immutable manifest revision whose adapter and discovered LEDGER versions remain compatible, when commit starts, then INGEST validates its fingerprint, approval, versions, account state, and candidate identities before the first mutation.
2. Given an accepted candidate, when it is committed, then INGEST invokes only the public LEDGER transaction-recording operation with the frozen request, statement-import provenance, and a stable candidate idempotency identity.
3. Given an Exact Duplicate outcome, when commit traverses the manifest, then INGEST records the prior canonical reference and invokes no new LEDGER write for that candidate.
4. Given a successful LEDGER result, when INGEST records the outcome, then the returned stable transaction reference round-trips through the public LEDGER read contract with the approved immutable facts.
5. Given a LEDGER validation, compatibility, or idempotency conflict for a candidate, when commit receives it, then INGEST durably records the stable outcome and stops before unsafe continuation.

### FR-INGEST-ARTIFACT-CLEANUP: Abandon and clean up ingestion artifacts safely

- **Priority:** High
- **Description:** Remove extraction temporaries deterministically, retain only the state needed for review or resume, and allow explicit owner cleanup without changing the source or canonical LEDGER effects. Implements UC-INGEST-005 under A4.
- **Rationale:** Sensitive temporary data must not linger, while premature deletion must not destroy recoverability.

**Acceptance Criteria:**

1. Given preview, commit, failure, or abandonment reaches a boundary where no unresolved candidate can still require temporary extraction data, when cleanup runs, then INGEST removes those temporaries deterministically and retains no caller-owned source copy.
2. Given a crash left known temporary artifacts, when the next INGEST invocation acquires the artifact-cleanup lock before workflow processing, then cleanup identifies and removes only orphaned INGEST temporaries without touching sources, manifests required for resume, receipts, or LEDGER data.
3. Given an incomplete batch, when the owner explicitly abandons it, then INGEST records abandonment, prevents future commit or resume for that manifest revision, removes disposable temporaries, leaves prior canonical transactions unchanged, and leaves the source untouched.
4. Given an incomplete manifest or receipt still required for review or resume, when cleanup is requested, then INGEST rejects destructive cleanup with a stable retained-for-recovery result.
5. Given a completed metadata-only receipt or safely abandoned batch, when the owner explicitly requests cleanup, then INGEST removes only the selected retained INGEST artifacts and reports the result without deleting any canonical transaction or caller-owned source.

## Glossary

| Term | Definition |
|------|------------|
| **Candidate Transaction** | A normalized transaction proposal produced from one source row or source record. It retains provenance and validation state and is not canonical until accepted through the public LEDGER contract. |
| **Exact Duplicate** | A Candidate Transaction whose variant-defined Source Row Identity and source-derived financial facts match a prior canonical effect exactly. Only this identity-grade match may be suppressed automatically. Avoid: likely duplicate, fuzzy match. |
| **Exact Replay** | A new ingestion attempt whose Source Fingerprint, selected account, adapter version, and LEDGER contract version reproduce a prior batch identity exactly, regardless of filename, so the prior outcome can be returned without new canonical effects. Avoid: Exact Duplicate, which is a row-level financial identity claim. |
| **Format Variant** | A specific, detectable statement layout and encoding contract supported by one Source Adapter version; sharing a file extension does not make two layouts the same variant. |
| **Import Batch** | One immutable, reviewable ingestion attempt for a specific source artifact using a recorded adapter version and LEDGER contract version. It contains candidates and reconciliation evidence but does not itself imply LEDGER mutation. |
| **Import Manifest** | The immutable record of source fingerprint, adapter and contract versions, candidate mappings, validations, reconciliation evidence, and intended idempotency keys reviewed before commit. |
| **Import Receipt** | The durable machine-readable outcome of commit, mapping each candidate to its canonical LEDGER result or explicit unresolved state so an interrupted operation can resume safely. |
| **Overlap Conflict** | A candidate that resembles or shares a statement window with a prior transaction but lacks exact identity evidence, or reuses an identity with different facts. It blocks automatic commit. Avoid: duplicate, because that would overstate certainty. |
| **Passive Parsing** | Reading bounded document values without executing formulas, macros, scripts, hyperlinks, embedded objects, or remote fetches. Avoid: opening or rendering, which can imply active behavior. |
| **Reconciliation Evidence** | Source-provided controls such as row counts, debit and credit totals, opening and closing balances, page counts, or sequence markers used to prove extraction completeness for an import batch. It is not ongoing account balance reconciliation. |
| **Reviewed Manifest Revision** | The exact immutable Import Manifest version inspected and explicitly approved for commit. Any changed account mapping, eligibility decision, adapter version, or contract version requires a new revision and preview. Avoid: current batch when the revision is not named. |
| **Source Adapter** | A versioned local parser and normalizer for one evidenced bank format variant. It recognizes that variant explicitly and fails closed on unsupported layout changes. |
| **Source Fingerprint** | A deterministic identifier derived from the source artifact for exact-file replay detection. It is not, by itself, proof that two financial transactions are duplicates. |
| **Source Row Identity** | The provenance key that identifies a transaction-bearing record within its source context across retry and resume. Its components are format-specific and are established during discovery. |
| **Terminal Candidate Outcome** | A durable receipt result proving that one candidate was accepted into LEDGER, returned as an Exact Duplicate, or left blocked/rejected without mutation. A blocked or rejected transaction-bearing record keeps that manifest uncommittable and requires a new reviewed resolution. Avoid: processed, which does not state the financial effect. |
